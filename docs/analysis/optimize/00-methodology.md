# 评估方法论（v3.3 — 真相源）

> **Roadmap**：`docs/backlog/optimization-audit-roadmap.md`（v3）
> **状态**：M0.2 done（v3.3 收敛：单一参数源、移除幻影类型、补 XMeta/xpt/i18n、优化机会 8+8、抽查式审查、四大量表、维度编码）
> **本文档是 4 个评估文档的真相源**——`optimization-audit-roadmap.md` / `00-checklist.md` / `README.md` 均应**引用本文档**而非复述内容。
> **目的**：为每个独立子 agent 提供调研框架与产出标准
> **重要提醒**：本方法是**参考框架**，不是天花板。子 agent 应在此基础上发挥**独特洞察**，发现框架未覆盖的别扭模式与改进机会。

## ⚠️ 重要：方法论是脚手架，不是天花板

> **给子 agent 的提醒**：
>
> 本方法论定义了**调研清单**（必读文件）、**产出清单**（必含内容）、**反空话门槛**（最低标准）。
>
> 但**真正有价值的发现往往在框架之外**：
>
> - 本方法论无法预测每个域的"独特别扭模式"——子 agent 应在调研中主动识别
> - 本方法论的 12 类别扭模式清单是"通用模板"，子 agent 应发现**本域特有的别扭模式**
> - 本方法论的优化建议清单是"示例"，子 agent 应挖掘**更深层的改进机会**
> - 子 agent 应在调研中**质疑框架本身**——如果发现框架的某条标准不适用本域，应在评估文档中说明并提出替代标准
>
> **底线**：满足框架最低门槛 + 发挥独特洞察 = 合格的深度评估。

   - 非常规检查：grep `ErpMd*` 与各域 `Erp*` 同名字段，对比重复定义
   - 同步机制：手工 / 事件 / ETL / 不存在
2. **字段缺失**
   - 非常规检查：owner doc 描述的字段 vs orm.xml 实际字段差异
   - 业务流程所需的"快照"字段（如 `committedAmount` / `originalBillCode`）
3. **类型精度不当**
   - 非常规检查：跨域金额精度对比（18/2 vs 20/4）
   - 是否有 VARCHAR(4000) 滥用或数值类型过小
4. **关系设计不当**
   - 非常规检查：cascade-delete 在保留历史的实体上是否误用
   - 跨域 FK 软引用 vs 硬引用对比
5. **索引缺失/冗余**
   - 非常规检查：基于 E2E 测试识别高频查询路径
   - 复合索引顺序是否最优
6. **字典设计不当**
   - 非常规检查：跨域 dict 同名异义 / 同义异名对比
   - dict 死状态（option 未被任何 BizMutation 引用）

### 业务逻辑层（4 类）

7. **tryPost 吞异常致业财过账悬挂**
   - 非常规检查：grep `tryPost` + 检查 catch 块是否吞掉异常
   - 单据进入已过账状态但实际未过账的实例
8. **approveStatus vs docStatus 双轴割裂**
   - 非常规检查：grep 双轴状态迁移是否同步
   - 是否有"docStatus=POSTED 但 approveStatus 仍是 DRAFT"
9. **daoFor() 滥用**
   - 非常规检查：grep `daoFor(Erp` 全仓 + `IErp*Biz` 注入对比
   - 是否有绕过 I*Biz 的实例
10. **业务流程"绕弯"**
    - 非常规检查：每个 BizMutation 的行数是否 > 200
    - 是否有重复样板代码

### 横切层（2 类）

11. **状态字段命名分裂**
    - 非常规检查：grep `status` vs `docStatus` vs `state`
    - 同概念不同命名的全仓分布
12. **跨域实体重复定义**
    - 非常规检查：跨域实体对比表
    - 数据冗余风险评估

> **子 agent 应在此基础上发现本域特有的额外别扭模式**。

## 6. 数据量估算口径（v3.1 强化：模板化）

### 7.2 双独立子 agent 审查流程（v3.2 改为**抽查式审查**）

> **v3.2 重要修订**：原 v3.1 "第二子 agent 先独立调研再交叉对比"导致审查工作量 ≈ 调研工作量（重复劳动），改为**抽查式审查**。

**Step 1：第一独立子 agent**
- fresh session 启动
- 执行深度调研 + 产出评估文档
- 提交 `domain-NN-*.md` / `biz-NN-*.md` / `cross-NN-*.md` / `ui-NN-*.md`

**Step 2：第二独立子 agent（审查者，抽查式）**
- fresh session 启动
- **不重复调研**，而是对第一子 agent 产出做**抽查式核验**：
  - 读第一子 agent 的"调研足迹"列表
  - **抽样规则（固定、非可选）**：
    - **P0 优化机会项全部抽查**（逐条实读其 file:line 引用）
    - 其余从 P1/P2 项中**随机**补足至总计 8 处（若 P0 已 ≥ 8 则只查 P0）
  - **实读核验**：亲自读这 5-8 处文件:行号，验证子 agent 的引用是否准确（引用存在、行号对应、描述与代码一致）
  - 抽查优化机会表 8 个必填字段是否齐全（结构化检查）
  - 抽查 mermaid 流程图是否对应代码（按图内 `// file:line` 注释核验）
- 产出 `*-review.md`（独立成文件）包含：
  - 调研足迹是否达到深度门槛？（结构化检查：类型数 + 行数）
  - 产出清单 11 节是否齐全？（结构化检查）
  - 反空话门槛是否通过？（结构化检查：是否有"建议优化索引"类空话）
  - "独特洞察"是否达到分级门槛？（结构化检查：条目数 + 是否附"发现方法"）
  - **抽查核验结果**：8 处中引用准确数 + 引用准确率
  - 优化建议是否可行？（仅对 P0 项做实质判断，其余不做实质判断）

**Step 3：执行者裁决（判定唯一化，v3.3 修复重叠）**

先计算两个独立指标：
- **A = 抽查引用准确率** = 准确数 / 抽查总数
- **B = P0 项实质分歧数**（仅对 P0 项由审查者记录的实际分歧）

判定（按顺序，命中即停）：

| 优先级 | 条件 | 裁决 |
|--------|------|------|
| 1 | A ≥ 0.8 且 B = 0 | **done** |
| 2 | A ≥ 0.5 且 B ≤ 1 | 执行者裁决（对分歧项逐条裁定） |
| 3 | A < 0.5 或 B ≥ 2 | **第一子 agent 返工** |
| 4 | 返工后仍落在条件 3 | 引入**第三独立仲裁**（不重复调研，仅裁决） |

> **v3.3 修复**：原 v3.2 用"P0/P1 差异数 或 抽查错位"两个维度组合，在 3-4 错位时同时落两档。现改为**引用准确率 A + P0 分歧数 B** 的单一有序判定，无重叠区间。

## 8. 输出风格约定

1. **简洁**：每发现用 1-3 句话表达
2. **具体**：发现必须指向具体文件/行号/实体名/方法名
3. **可追溯**：每条发现必须可追溯到数据来源
4. **不重述**：不重述 owner doc 内容，只评估"是否最优"
5. **优先级标注**：每条发现必须有优先级（P0-P3）+ 风险 + 工作量
6. **数据量必填**：每实体必填数据量估算（含区间 + 公式 + 增长曲线）
7. **契合度必评**：每个核心实体必填契合度评级

## 9. 评估硬约束

1. **不引入代码/配置/ORM/契约变更**——所有"建议"为文档级输出
2. **不重复既有审计/分析**——仅识别"非缺陷但可优雅化"的设计层问题
3. **每个子 agent 必须达到深度门槛**——未达门槛必须返工
4. **关键工作项必须双独立子 agent 审查**——未通过审查必须重新调研
5. **保护区域建议须标注**——任何触及 ORM/api.xml/auth/permissions/accounting/finance postings 的建议，归 `plan-first` 或 ask-first
6. **优化机会 auditRef 默认填 `NEW`**——M5 汇总时统一去重（子 agent 不必搜索既有 ID）

## 10. 给子 agent 的最后提醒

> **本方法是脚手架，不是天花板**。
>
> 真正有价值的评估来自子 agent 的**独特洞察**——那些不在框架清单中、但确实存在于代码中的别扭模式。
>
> **鼓励**：
> - 质疑框架的标准
> - 发现框架未覆盖的别扭模式
> - 提出比框架建议更深入的改进方案
> - 跨子 agent 关联发现
>
> **底线**：框架最低门槛 + 独特洞察 = 合格的深度评估。

## 11. 量表与编码（v3.3 增补）

### 11.1 术语表

| 术语 | 定义 |
|------|------|
| **业务需求-模型契合度** | 当前 ORM 模型对业务需求的表达效率——是否"恰到好处" |

### 11.2 业务需求-模型契合度 4 级量表（v3.3 增补）

对每个核心实体按下表落级（4 个维度分别判定，取最差级为总级）：

| 级别 | 字段完备性 | 关系合理性 | 索引覆盖 | 字典/跨域一致性 | 含义 |
|------|-----------|-----------|----------|-----------------|------|
| **优** | 业务字段 100% 覆盖 | 无 cascade-delete 误用 | 高频查询全有索引 | 字典无死状态 + 跨域 FK 走 notGenCode | 无需调整 |
