## 维度 2 — propId 连续性 + 长度精度

### 2a. propId 连续性

**扫描器原始输出**：33 个「blocker」（propId 不从 1 严格连续）。

**手工 FP 核实**：逐项核查全部 33 个，**全部为 false positive**，分两类：

1. **保留区间模式（reserved range，Nop 平台接受）**：propId 主段连续，然后跳到高号段为 delta 扩展/后加字段预留。例：
   - `ErpAstMovement`：1-27 连续，然后 200/201（`approvedBy`/`approvedAt`，delta 扩展字段）
   - `ErpHrSalary`：1-19 连续 → 跳 28-45（业务字段）→ 跳 90-92（approvedBy/approvedAt/businessDate）
   - `ErpMfgMaterialIssue`/`ErpPrjBudget`/`ErpPrjCostCollection`/`ErpPurRfq`：propId 200/201 为预留扩展位
2. **审计字段隐式注入**：部分实体通过 `useLogicalDelete="true" deleteFlagProp="delVersion"` 等实体级属性隐式声明审计字段（delVersion/version/createdBy/createTime/updatedBy/updateTime），这些字段在框架层有保留 propId 但无显式 `<column>` 标签，扫描器仅计显式列故误报 gap。

**关键验证 — propId 重复检测（真实 blocker 条件）**：独立脚本扫描全 19 orm.xml 351 实体，**propId 重复数 = 0** ✅。

**权威证据**：154 模块 `mvn clean install -DskipTests` BUILD SUCCESS（Nop codegen + ORM 模型校验通过）。Nop 平台对 propId 的实际约束是**唯一性**（不可重复），非严格连续性——保留区间是平台支持的向后兼容模式（字段删除后不重编号）。已知失败模式 #8（"propId 编号断续"）的实际语义是「不可有重复」，非「不可有 gap」。

**裁决：✅ 通过**（0 真实 blocker；33 个扫描器原始 blocker 全部为 FP，已逐项核实）。

## 扫描器测量口径限制记录（供后续审计参考）

本次扫描器的原始 blocker/major 全部为 FP，根因是扫描器测量口径不足：

1. **propId 连续性**：扫描器假设严格从 1 连续，未识别 Nop 平台支持的「保留区间 + 唯一性」实际约束。**改进建议**：未来扫描器应检测 propId **重复**（真实 blocker）而非 **gap**（平台允许）。
2. **dict 引用完整性**：扫描器仅扫描项目 orm.xml `<dicts>` 段，未识别两种合法 dict 来源：① 平台模块字典（`nop-wf`/`nop-auth` 等 `wf/`/`nop-` 前缀）；② 独立 dict.yaml 资源文件（`erp-*-meta/src/main/resources/_vfs/dict/`）。**改进建议**：未来扫描器应聚合项目 orm.xml + 平台 orm.xml + 独立 dict.yaml 三源。
3. **to-many cascade-delete**：扫描器未区分树形自引用（应禁 cascade-delete）与头-行关系（应 cascade-delete）。**改进建议**：refEntityName == 自身 className 时跳过 cascade-delete 检查。

## 残留风险

2. **扫描器改进**：上述 3 项测量口径限制若不修正，未来审计会重复产生 FP 噪音。可考虑提升为 `docs/audits/` 下的改进任务。
