# Lesson 25: 结束审计门控被执行者预勾——批量勾选检查框时未保护审计门控

> **来源**：2026-09-27/28 perf-ux mission 内**两次独立发生**——批次 2 plan `2026-09-27-0325-2` round 1 结束审计（审计方判程序违规，门控被取消勾选整改）；批次 4 plan `2026-09-28-0852-2` 结束审计（Blocker B1：执行者用批量 sed `- [ ] → - [x]` 置位全部完成项时未排除结束审计门控，被审计方再判 Blocker）。两次均非主观自我审计，而是**机械操作覆盖了程序门控**。
> **适用场景**：任何执行者在计划接近完成时批量更新检查框/状态的场景——`sed`/编辑器全量替换、复制上一批的门控模板、「顺手勾完」。
> **失败模式**：结束审计门控「结束审计由独立子代理执行；执行者未自我审计」在审计实际发生前被置位，与 Closure Audit Evidence 占位行自相矛盾——审计章程明文「执行者预勾 = Blocker」，导致一轮完整审计往返浪费。

## 核心论点

门控的价值在于其状态只能由门控事件本身置位。批量文本变换不区分「执行者可自证的完成项」与「必须由外部事件触发的门控项」——把后者纳入批量替换范围，等于用机械操作冒充门控事件，即使执行者主观上并无自我审计意图。

## 防御规则

1. **批量勾选的排除集**：对计划文件做任何形式的批量检查框置位（sed/脚本/编辑器多光标）前，先列出「门控类检查框」（结束审计门控是本仓唯一硬门控），将其排除在替换模式之外——例如先用占位符替换门控行再批量替换，或替换后立即 grep `结束审计由独立子代理` 验证其状态。
2. **置位前自检三问**：该门控断言的事件（独立审计）是否已实际发生？Closure Audit Evidence 是否仍是占位符？日志条目是否仍写「待独立结束审计」？三者与门控状态不一致 = 预勾。
3. **审计方的廉价前置检查**：结束审计代理开场即核对「门控是否预勾且证据行是否占位」——两处状态矛盾即可判 Blocker，无需等全量审查（本仓两次均由审计方按此路径捕获）。
