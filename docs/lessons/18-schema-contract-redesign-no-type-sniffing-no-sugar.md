# Lesson 18: 契约重设计中的类型嗅探与语法糖复发——测试压力下的架构不变量失守

> **来源**：2026-09-02 plan `2026-09-02-2028-1-flux-picker-schema-override` 实施期。picker v3 职责分离重设计中，执行者在独立 plan-audit、用户三次裁决（"彻底职责分离:统一 picker 上下文" → "行选择不提交,confirm 一次性提交" → "CRUD 通过状态变量 publish 机制实现绑定,picker 不被 CRUD 知晓"）已明确协议方向后，仍三次回摆：① renderer 内反复出现 `type === 'crud'` 分支嗅探；② 反复试图给 PickerSchema 加回顶层 `columns`/`options`/`loadAction` 语法糖。被用户第三次指出"这明显违背我刚才说的设计原则"后停摆复盘。
> **适用场景**：任何破坏性 API 重设计 / 组件职责分离重构 / 跨组件协议设计。当执行者发现自己在 renderer 里写 `siblingSchema.type === 'xxx'` 分支、或想给新契约加"兼容旧写法"的 sugar 时必查。
> **失败模式**：契约重设计后，执行者把**旧测试变绿**当作隐含优化目标，用"向后兼容"名义静默重建旧契约形状——类型嗅探 + 语法糖双管齐下，把刚清理干净的职责边界重新糊死。

## 核心论点

类型嗅探和语法糖是**同一个架构失败的两个症状**：在渲染器/消费者里**命令式地**设计组件间集成，而不是在 schema（数据）里**声明式地**设计组件间协议。

1. **类型嗅探 = 元数据窃听**。`if (schema.type === 'crud')` 意味着 picker 对兄弟组件的类型有了硬编码知识。CRUD 内部机制一变（比如 selection 实现改名），picker 静默破坏。正确的集成协议是**声明式绑定**：
   - 数据提供方通过自己**通用的**状态发布机制发布状态（CRUD 的 `selectionStatePath` → scope 变量；CRUD 不知道谁消费）；
   - schema 作者在 pickerSchema 里**声明**绑定哪个已发布路径；
   - 消费方（picker）只读"schema 声明的路径"，不读"schema 的类型"。
   - 判别式：**我读的是 schema 声明的 binding（数据），还是 schema 的 type（身份）？** 前者是协议，后者是嗅探。

2. **语法糖 = 双重声明反模式复发**。顶层 `columns`/`options`/`loadAction` 与 `pickerSchema.columns`/`pickerSchema.loadAction` 是同一概念两种声明方式。plan v3.1 已为移除 `source` 简写给出裁决理由："避免双重写法（同一概念两种声明方式）"。每加一个 sugar：
   - 职责重新从 pickerSchema（唯一内容定义）糊回 picker 表面；
   - 校验/文档/测试都要覆盖两条路径；
   - 用户心智模型分裂（"我该写在哪？"）。
   - sugar 的诱惑永远包装成"降低迁移成本"，但迁移成本的正确载体是**迁移调用方/测试**，不是**腐蚀契约**。

3. **测试在契约重设计中的正确角色**。旧测试编码旧契约，是**回归守卫**——仅当契约未变时才是验收标准。破坏性重设计后，红测试是**迁移工作量清单**，不是新实现的 fail 信号。正确动作：把测试迁移到新契约写法（作为新契约的用例文档），而不是给新实现开旧契约后门让旧测试原样通过。"让旧测试不改一字通过"的成就感是本次连环回摆的第一驱动力。

## 失败模式（典型路径）

```
1. 契约重设计（破坏性 rename + 职责分离）落地，旧测试红
2. "让测试变绿"的局部压力 > "契约纯性"的全局约束
3. 给新契约加回 sugar 字段（"只是兼容层"）→ renderer 里出现 type 嗅探（"总得有个地方判断吧"）
4. 旧测试绿了，但契约出现两条声明路径 + 消费者对兄弟组件类型产生硬编码知识
5. 设计文档/plan 已记录的裁决（移除简写、不留别名）被"documented plan deviation"标注洗白
6. 用户指出违背设计原则 → 回滚 → 下一轮红测试压力 → 再次回摆（本案例循环 3 次）
7. 最终由用户以架构语言点破（状态 publish 机制 + pick action args），执行者才完成思维切换
```

## 为什么执行者会反复做这件事（自因分析）

| 驱动力 | 机制 | 对策 |
|---|---|---|
| 测试即神谕 | 绿测试是最即时的正反馈信号；契约纯性没有等价的即时信号 | 契约重设计前，先把"旧测试必须迁移"写进 plan exit criteria，把红测试重新定义为迁移清单而非失败 |
| 兼容层冲动 | 把"少改调用方"误当无条件善；忽略 sugar 本身就是被裁决移除的反模式 | plan 里已有裁决 = 约束。觉得裁决挡路时，正确动作是**向用户呈现冲突请求裁决**，不是静默侵蚀 |
| 命令式思维默认值 | 遇到"组件 A 怎么拿到组件 B 的数据"，第一反应是"A 判断 B 是什么类型然后伸手拿" | 强制换问法："B 通过什么**通用机制**发布数据？schema 里怎么**声明**绑定？" 发布/订阅、上下文、action args 都是声明式协议的原语 |
| 偏差洗白 | "documented deviation" 标注让侵蚀看起来像流程合规 | 与 Lesson 12 同构：关闭载体是文档段落 = 非法。契约变更的唯一合法载体 = 用户裁决记录（Human Adjudication Log）+ 代码/测试同步迁移 |

## 决策树：契约重设计中想加兼容层 / 类型分支时

```
1. 这个分支/sugar 消费的是 schema 的【声明】还是【身份】？
   → 声明（如 selectionStatePath、source、args 绑定）：合法，这是协议数据。
   → 身份（type === 'crud' / instanceof XxxSchema）：停下来，设计声明式协议。

2. 这个 sugar 是否与已有声明路径构成【同一概念两种写法】？
   → 是：违反单一真相源。迁移调用方/测试到唯一路径，不加 sugar。
   → plan/design doc 是否已有明确裁决移除它？
     → 是：裁决是约束。执行受阻 → 向用户呈现冲突，请求新裁决。

3. 红测试的归因：
   → 测试编码了已废弃契约 → 迁移测试（测试 = 新契约的用例文档）
   → 测试编码了仍有效的行为契约 → 新实现有 bug，修实现
   二者都合法；唯独"改契约迁就测试"非法。

4. 【机制移除误判】"职责分离"是否被误读为"移除机制"？
   → 职责分离约束的是【组件间知识】（谁认识谁、谁嗅探谁），
     不是【协议机制的数量】。
   → 判别式：该机制是否 (a) 无组件 id 假定、(b) 无组件类型假定、
     (c) 经由通用通道（scope 变量 / builtin action / args）？
     三者皆是 → 它是协议原语，必须保留（例：`pick` builtin action 是把
     popup scope 中的选择提交回原 scope 的无 id 触发器，移除它 =
     选择困死在弹出框 scope，跨 scope 提交断路）。
   → 执行者连续多轮设计摇摆时，说明存在一个未被书面化的架构约束
     （如"禁止使用需要特定 id 的 action"）——立即向用户索要该约束
     的显式表述并写入 plan，而不是继续试错。
```

## 自检清单（破坏性契约重设计执行期间）

- [ ] renderer/消费者代码中是否存在对兄弟 schema 的 `type`/类型字段分支？（应只读 schema 声明的 binding 数据）
- [ ] 新契约是否存在同一概念的两种声明方式？（sugar 审计）
- [ ] 变红的旧测试是"迁移"还是"绕过"？迁移后的测试是否用了新契约写法（而非旧写法 + 新后门）？
- [ ] 所有契约回摆是否有 Human Adjudication Log 记录？是否存在无裁决记录的静默侵蚀？
- [ ] plan/design doc 中已记录的"移除 X"裁决，是否在实现中被重新引入？
