# Lesson 21: 规范成文先于符合性审计——无成文标准的审计没有判定准绳，也没有修复授权

> **来源**：2026-09 ai-check-r3 mission（roadmap `docs/backlog/ai-check-r3-roadmap.md`）MV.3 方法学沉淀（plan `2026-09-11-0906-3`）。证据基 = M0.1 反事实对照：`docs/architecture/i18n-compliance.md`（M0.1 产出）+ `m0-5-audit-checklists.md`（M0.5 五维冻结清单）+ MI.2~MI.6 修复批与 M1.x DIM-I 维零标准争议实录。
> **适用场景**：任何符合性审计 mission 的开工前；任何"审计 finding 引发修复但争议不断/复判反复"的领域；任何计划把"语言/风格/合规边界"类裁决留到"边审边定"的路线图。
> **失败模式**：标准不成文就开审——finding 无判定准绳（这算不算违规？），修复无授权（按什么改？改成什么样子？）；每个审计切片自行解释标准 → 同型站点不同裁定（标准漂移）；修复批与审计批互相争议，返工与信任损耗。

## 核心论点

**审计产出的是"违判定"，修复消费的也是"违判定"——判定准绳本身就是关键生产资料，必须先于审计被生产出来。**

反事实实录（F15）：i18n 国际化工作项（`frontend-ui-roadmap.md` F15，plan `2026-07-23-0818-1`，view.xml 层 351 文件 1340 处全覆盖）曾将**后端消息**明确列为 Non-Goal（page.yaml title 同样 Deferred）。根因不是能力不足，而是**标准不成文**——彼时全 docs 树没有任何日志语言/i18n 边界规定（LOG 该不该中文？异常参数呢？`@Description` 呢？）。无标准则：F15 的 Non-Goal 边界无法被审计挑战（没有"违判"依据），后端消息的清剿也无从授权（改成英文还是走 i18n？`ErrorCode` 中文描述算不算违规？）。两年内 r1/r2 审计多轮触达相关面而从未立项清剿，即此根因。

## 方案三步（r3 验证有效的成文先行协议）

| # | 步骤 | r3 落地形态 | 防的失败 |
|---|------|------------|----------|
| 1 | **权威 owner doc 成文 + 判定冲突唯一权威声明** | M0.1 立 `docs/architecture/i18n-compliance.md`：8 类判定准绳表（每条含判定规则 + 依据指针）+ 白名单登记格式（四要素）+ 修复模式对照表（CAT-1..4 逐类修复模式与关键边界）；头部声明"判定冲突以本文档为准"；roadmap 规则 5 同此声明 | 判定依据散落聊天记录/PM 原文/各切片口头裁决 → 同型不同判 |
| 2 | **成文时点快照冻结，防真相源漂移** | M0.1 成文同时，此前散在 roadmap 内的合规基线裁定表**冻结为历史快照、不再更新**（双重真相源 → 单一权威收敛）；owner doc 自身**不内联任何探针计数**作准绳（口径敏感快照只作历史对照），权威口径指向脚本 + 基线文件（互链 lesson 13：计数型断言一律指向权威计数源，不内联复制） | 两处写同一裁定 → 漂移后消费者各取其一；内联计数 → 实现演进后静默陈旧被当前提消费 |
| 3 | **检查清单冻结后才开审计** | M0.5 冻结五维（后端/前端/seed/单测/i18n）× 21 核对单元清单 `m0-5-audit-checklists.md`（105 基础格 + 跨轮查重 + S 级切片唯一归属），作为 M1.1~M1.16 全部审计切片的强制核对矩阵——矩阵先冻结，切片后执行 | 边审边定维度与口径 → 切片间不可比、覆盖不可证、漏格不可查 |

## r3 案例实录（成文先行 → 零争议复判）

- **修复批直接消费成文裁定**：MI.2~MI.6 各清剿批（CAT-1 335→0 / CAT-2 204→0 / CAT-3 390→0，分批对账见 lesson 20）的修复动作逐条对照 `i18n-compliance.md` 修复模式对照表执行——CAT-3 逐簇裁决的三选一（(a) 字典回归 / (b) 英文化 / (c) 白名单登记）与混合文件规则 (i)(ii)(iii) 均在 owner doc 内预裁定，批内只做"站点 → 模式"映射，不做标准再创造。
- **审计维零标准争议**：M1.x 五维矩阵 DIM-I 维全程零标准争议复判——各切片判定直接引用准绳表 #1~#8（如 `@Description("中文")` 按准绳 #5/E3 豁免、`ErrorCode` 中文描述按 #1 合规），28 份 `ck-*` 报告无一起"这算不算违规"的 finding 争议。
- **白名单四要素核验可行**：因为登记格式先成文，MV.1/MV.2 终态核验才能对 27 条白名单做机械核对（四要素缺一不可），豁免与违规的边界全程无人工争论。
- **对照面**：M0.1 之前，roadmap 内的合规基线表与后续成文标准并存过双重真相源风险——成文时点冻结历史快照后收敛为单一权威，后续 MI/MV 各批从未出现"以哪张表为准"的争议。

## 与既有 lesson 的划界

| Lesson | 关联与划界 |
|---|---|
| Lesson 12（documented simplification 滥用） | **成文标准不是文档化简化的挡箭牌**：owner doc 成文的是"判定准绳"，不是"关闭载体"——分歧的合法关闭载体仍是代码行为（lesson 12 判别式）；把违规写进白名单（带四要素裁决）≠ 用一句 Non-Goal 掩盖功能缺失。准绳让"豁免"变得严格可审，恰恰压缩了方案 B 滥用空间 |
| Lesson 13（需求基线陈旧） | 步骤 2 的机制依据：成文标准若内联计数/快照型断言，实现演进后同样静默陈旧被当前提消费。r3 的防御 = 标准 doc 只写判定规则（稳定面），计数指针化指向脚本 + 基线文件（演进面） |
| Lesson 20（脚本基线门控） | 本课的下游：成文标准定义"什么算违规"（判定面），脚本基线门控实现"违规归零且不回潮"（执行面）。标准先不成文，脚本的 CAT 分级与白名单就没有裁决依据可登记 |

## 自检清单（审计 mission 开工前三问 + 两查）

**三问（答不出任何一问 = 不具备开工条件）：**

- [ ] **标准在哪？**——判定准绳落在哪个权威 owner doc（文件路径可指）？还是散在 roadmap/聊天记录/口头？
- [ ] **谁裁决？**——每类判定的依据指针（用户裁定原文/平台文档/既有 owner doc）是否逐条可溯？
- [ ] **冲突以谁为准？**——是否显式声明唯一权威 + 旧表述冻结为历史快照（无双重真相源）？

**两查（成文质量）：**

- [ ] 标准 doc 是否只写稳定判定规则、不内联探针计数（计数指针化指向权威源，防 lesson 13 陈旧）？
- [ ] 核对清单/覆盖矩阵是否在第一个审计切片执行**之前**冻结（矩阵先于切片，覆盖可证）？

**边界自查：**

- [ ] 成文标准是否被用作关闭载体的挡箭牌？（对照 lesson 12 判别式：关闭载体是代码行为还是文档段落？）
