# Lesson 20: 机械类违规须脚本基线门控而非抽样审计——确定性清剿五要素

> **来源**：2026-09 ai-check-r3 mission（roadmap `docs/backlog/ai-check-r3-roadmap.md`）MV.3 方法学沉淀（plan `2026-09-11-0906-3`）。证据基 = r3 主线实绩：M0.2 交付 `tools/check-hardcoded-cjk.mjs`、M0.3 冻结 `docs/audits/cjk-baseline.md`、MI.2~MI.8 分批清剿后 CJK 终态行（`docs/testing/known-good-baselines.md` 2026-09-08 `ai-check-r3` MI 终态行 / 2026-09-11 `ai-check-r3-mv1` 终态行）。
> **适用场景**：违规面**机械可判定**（硬编码中文、`@Inject private`、缺失注解、裸 `System.currentTimeMillis()` 等——存在性可被 grep/AST 判定，无需人类语义裁决）且存量量大、跨多模块的清剿任务；以及任何"审计发现同一类问题反复出现"的领域。
> **失败模式**：用抽样式审计对付机械类违规——样本没抽到的文件持续带病存活，多轮执行后问题依然存在；修复批无机器门控，修复后新改动又悄悄回潮（无防复发机制）；豁免走口头裁决或散落注释，无唯一登记通道。

## 核心论点

**抽样审计的置信度永远 < 100%，而机械类违规恰恰是唯一可以被 100% 判定的违规类别**——"有没有中文硬编码"不需要语义理解，只需要全量扫描。对这类违规做抽样，等于放弃了自己独有的确定性能力。r1/r2 两轮审计的动机缺陷正在于此：执行过多轮，硬编码中文始终存在，因为每轮都在抽样，从未全量。

**脚本绿 = 闭环**：`actual ≤ baseline` 的机器断言替代"本批看起来修完了"的人类断言。审计论点从"我抽查了 30 个文件没发现问题"变为"全仓 3430 Java + 886 yaml 扫描零违规，且 CI 门的单向收紧保证它不会回潮"。

## 方案五要素（r3 验证有效的完整闭环）

| # | 要素 | r3 落地形态 | 反面（缺此要素时） |
|---|------|------------|-------------------|
| 1 | **全量扫描脚本** | `tools/check-hardcoded-cjk.mjs`——扫 main Java（排 `target/`/`_gen/`/`src/test/`/注释行）+ `*.page.yaml`/`*.flux.yaml` | 抽样 → 漏网文件带病存活，"多轮执行仍有问题" |
| 2 | **违规分级（CAT）** | 五类分级：CAT-1 LOG 中文 / CAT-2 异常中文参数 / CAT-3 运行时字符串中文 / CAT-4 页面 yaml 中文无 i18nEn / CAT-5 注释（豁免不计） | 一刀切计数把"该修的"和"该豁免的"混在一起，修复批无法分批路由 |
| 3 | **基线快照 + 单向收紧门控** | M0.3 冻结 `docs/audits/cjk-baseline.md` §SNAPSHOT（机器可读块，`--baseline` 自动整体重生成勿手改）；`--strict` 逐文件逐 CAT 断言 `actual ≤ snapshot`，任何新增违规非零退出 | 无基线则"绿"无从定义；无单向收紧则修复成果静默回潮（对齐 `compliance-baseline.md` 范式：actual 只降不升，调高须独立计划裁决 + per-site 证据） |
| 4 | **anti-fake-green 自证** | `--self-test` 13/13 断言（checker 对注入样本必须报违规、对豁免样本必须放行）+ 文件注入重放（注入 CAT-1 样本 exit 1 → 移除恢复 exit 0） | checker 自身静默失效（正则写错/口径漂移）时全绿是假的——"门是绿的"≠"门在工作" |
| 5 | **白名单唯一豁免通道 + 批注账** | §WHITELIST 机器可读块四要素登记（文件路径/理由/owner doc 指针/裁决来源，缺一不可），只增不删；分批清剿进度记 `cjk-baseline.md` §批注账 | 豁免散落代码注释/聊天记录/计划正文，无法机器放行 → 全量扫描误报爆炸，被迫退回抽样 |

## r3 案例实录（CAT 终态对账链）

分批协议：**每批第一动作 = 脚本红线（该域当批 CAT 计数快照）→ 修复 → 该域归零 + 域测试绿 → 批注账登记**。四条对账链与 `known-good-baselines.md` MI 终态行/批注账逐值一致：

| 分级 | 基线（2026-09-06 冻结） | 终态 | 清剿批对账 |
|---|---|---|---|
| CAT-1 LOG 中文 | 335 | **0** | MI.2 93 + MI.3 165 + MI.4 77 |
| CAT-2 异常中文参数 | 204 | **0** | MI.5a 136 + MI.5b 68 |
| CAT-3 运行时字符串中文 | 390 | **0** | MI.6 批1 181（56 文件）+ 批2 209（88 文件，16 域归零 + 白名单全覆盖收官） |
| CAT-4 页面 yaml 中文 | 1700 | **0** | MI.8 批1 382（26 文件）+ 批2 1318（82 文件，17 域归零收官） |

- 基线快照初始 453 违规承载文件；分批修复后冻结快照收敛至 170 files（单向收紧：修复只减不增，`--strict` 终态 PASS exit 0，0 新增违规）。
- 白名单 27 文件（批1 11 + 批2 16）四要素齐备；`--self-test` 13/13（初版 10 + MI.8 批1 修复中扩 3 断言）。
- 每批"域测试绿"义务实证：MI.6 批1 fin/ast/cs 聚合 1047 tests 全绿；MI.6 批2 16 域聚合 2772/0/0；MI.8 批2 三阶段 775 + 1314 + 1101 全绿——清剿不破行为不变式（快照外科变换仅消息/名称列，seed CSV 零改动）。
- **门控抓真犯的实录**：MI.8 批1 首轮实跑 flux 导出 25 条错误 = 本批自身引入（`: ` plain scalar 语法错误 + 同 mapping 重复 `i18nEn` 键），原" stash 前后一致"注记被闭包审计**证伪**后由门控定位修复——机器门控抓住的恰恰是人类断言（"本批 0 错误"）说谎的地方。
- **快照保护实录**：MI.8 批2 批中一次子代理误触 `--baseline` 重生成冻结快照，当场 `git checkout` 还原后复验——基线文件是门控的锚，任何"顺手重新生成基线"都是单方放宽门控。

## 既有范式复用（不重建 checker）

新增脚本只补既有 checker 的**盲区**，不重复其覆盖面：

- `docs/audits/nop-compliance-checker.sh`（R1-R12 数值门控 + `compliance-baseline.md` §BASELINE 单向收紧）——反模式面先例；
- `docs/audits/i18n-coverage-checker.sh`（F15，view.xml/action-auth 层，anti-fake-green 注入验证纪律）——注入自证先例；
- r3 CJK 脚本补的盲区 = Java 运行时面 + page/flux yaml 面（F15 不扫这两面）。

## 自检清单

**何时该建脚本而非抽审：**

- [ ] 违规判定是否机械可判定（存在性可 grep/AST 判定，无需语义裁决）？是 → 抽样无正当性，建全量脚本。
- [ ] 存量是否跨多模块/量大（> 数十文件）？是 → 人工遍历不可持续，且修复批次需要机器红线。
- [ ] 是否已有 checker 覆盖此面？有 → 扩展既有脚本而非新建（避免双真相源）。
- [ ] 同类问题是否已反复出现 ≥ 2 轮审计？是 → 抽样已被证明无效，立即升级为脚本。

**新脚本的 anti-fake-green 义务：**

- [ ] `--self-test`（或等价注入重放）是否证明"注入违规必报、豁免样本必放行"？没有自证的脚本全绿不可信。
- [ ] 门控失效模式是否 fail-loud（解析失败 exit 2 而非静默 exit 0）？
- [ ] 基线文件是否禁止手改（机器整体重生成）+ 误改可 `git checkout` 还原复验？

**基线单向收紧纪律：**

- [ ] `--strict` 断言方向是否为 `actual ≤ baseline`（只降不升）？
- [ ] 调高基线是否走独立计划裁决 + per-site 证据（合法新增 baseline-raise vs 真违规 Fix 二分）？（见 lesson 07 决策树）
- [ ] 豁免是否只能走白名单唯一通道，且四要素（路径/理由/owner doc/裁决来源）缺一不可？
- [ ] 分批清剿是否每批记批注账（批前红线/批后计数/对账/验证），终态与 known-good-baselines 逐值对账？

> **2026-09-11 边界扩展注记（ai-check-r3 MG.1，plan `2026-09-11-1425-1`，CJK 白名单裁决范式归并裁决）**：本课第五要素「白名单唯一豁免 + 批注账」经 r3 全量实绩扩展边界——CAT-3 白名单逐簇裁决范式：C1 `@Description` 专属文件整档豁免 / C2 功能型中文内容契约窄类豁免（seed 角色名契约、中文发票 OCR 版式 Pattern、文档内容匹配——中文字面量即行为本体，改英文破坏行为）+ 混合文件「先修真实行后整档登记」规则（i）；批注账红线→归零对账闭环实绩：CAT-3 390→0 / CAT-4 1700→0 四批行、白名单 27 文件（批 1 11 + 批 2 16）四要素齐备。判定准绳权威 = `docs/architecture/i18n-compliance.md`（lesson 21 成文先例）；裁决来源 plan `2026-09-07-0902-1` Phase 1 Decision（MI.6 批 1，2026-09-07）。盘点结论：该范式与脚本门控耦合（白名单是 checker 的豁免通道），无独立复用面，故归并本课而非新立。本注记不重写正文。
