# Mission Driver 不是起点：从 Loop 控制到 Attractor-Guided Engineering 的关键澄清

> 写给读过《Mission Driver：Loop Engineering 的一种通用参考实现》和《Loop Engineering × Attractor》PPT 的读者  
>
> Mission Driver 解决的是“如何让 AI 持续运行”，Attractor 解决的是“持续运行究竟应该把系统带向哪里”。如果不区分这两个层次，就会把 AGE 误解成一个更复杂的 Agent 工作流。

## 一、为什么还需要这篇澄清

《Mission Driver》主要从工程实现出发，介绍了：

- Plan 如何定义一次变更的关闭条件；
- Mission Driver 如何自动审查、执行、起草和审计 Plan；
- 嵌套 Loop 如何实现恢复、隔离和局部容错；
- 文件状态如何支持跨进程、跨会话持续运行。

《Loop Engineering × Attractor》PPT 又向上增加了一层：Harness 只能控制执行，Attractor 才定义长期方向。

但两份材料放在一起，仍然容易产生几个误解：

1. AGE 是不是“工作流引擎 + 架构文档”？
2. Attractor 是不是换了名字的架构原则或控制目标？
3. Mission Driver 能稳定运行，是不是就意味着系统会自动收敛？
4. Plan、测试和独立审计都通过，为什么整体仍可能走错？
5. “Attractor Before Harness”是不是要求先设计完架构，再开始开发？
6. “AI 全自动开发”是不是意味着人可以彻底退出？
7. 为什么 AGE 要引入状态空间、轨迹、吸引子和控制，而不能继续使用需求、架构、任务和流程这些传统概念？

这些问题的根源在于：前两份材料很容易让人先看见 **Loop 的实现形式**，却没有充分看见 AGE 真正改变的是**软件工程的基础评价对象**。

Mission Driver 不是 AGE 的理论起点，而是 AGE 在控制层的一种实现。

---

## 二、真正的问题不是 AI 是否完成任务，而是系统正在走向哪里

传统 AI 开发主要围绕一次变更组织：

```text
提出需求
→ 生成代码
→ 运行测试
→ 修复问题
→ 宣布完成
```

即使引入 Spec、Plan、Review 和 Audit，关注点通常仍然是：

> 当前这次变更是否正确完成？

这是一种以**状态**为核心的评价方式：

- 当前代码能否编译；
- 当前测试是否通过；
- 当前需求是否实现；
- 当前 PR 是否符合规范；
- 当前 Plan 是否满足 Closure Gates。

这些检查当然必要，但它们无法单独回答另一个问题：

> 连续一百次局部正确的变更，正在把系统推向什么结构？

一个系统完全可能出现以下情况：

```text
每次提交都能编译
每个测试都通过
每项需求都得到实现
每次 Code Review 都没有发现明显问题
但模块边界正在模糊
事实来源正在分裂
测试正在和实现细节绑定
相同概念正在形成多套表达
旧的临时结构正在被不断固化
```

这里没有一个明确的“错误提交”。问题产生于多次合法变更的累积。

这就是**轨迹问题**。

AGE 的核心主张不是“传统软件工程从不关心演化”，而是：

> 过去由长期参与者隐式承担的轨迹判断，在 AI 成为高频变更主体之后，必须被提升为显式的一等工程对象。

---

## 三、AI 移除了传统工程中的一个隐藏前提

传统软件工程能够长期依赖状态级检查，是因为系统中通常存在一个没有被正式建模的连续主体：长期参与项目的人。

一个资深工程师会在头脑中持续保存：

- 为什么当初采用这种模块划分；
- 哪些边界不能被逐渐侵蚀；
- 哪些方案以前已经被证伪；
- 哪些临时实现不能变成长期结构；
- 哪些测试虽然通过，却正在与旧实现耦合；
- 连续几个 PR 是否正在形成错误趋势。

这种方向感并不完全存在于某一份 Spec、测试或架构图中。它分散在人脑、历史经验、口头交流和 Code Review 习惯里。

AI session 不具备这种天然连续性。

它具有几个不同于传统开发者的特征：

- 生成频率高；
- 单次改动范围大；
- 跨会话记忆不连续；
- 容易接受当前仓库作为天然正确的基线；
- 可以同时生成代码、测试、文档和完成说明；
- 局部输出往往非常自洽。

因此，AI 带来的特殊风险不是“更容易写出低级错误”，而是：

> 它可以高速地产生大量局部合理、彼此一致，但共同偏离长期结构的变更。

如果代码、测试、文档和验收说明都由同一理解产生，那么它们甚至可能一起错向自洽。

这就是为什么在 AI 开发中，仅仅加强测试、审查和 Guardrail 仍然不够。它们首先需要一个更高层的问题作为评价依据：

> 系统在长期演化中，应反复返回什么结构？

## 四、Attractor 究竟是什么

Attractor 不是最终要交付的一份功能清单，也不是某个固定版本的系统快照。

更准确地说：

> **Attractor 是一组定义长期结构同一性的高阶关系。局部实现可以变化，但系统在持续扰动中，应反复回到由这些关系定义的稳定结构族。**

通俗地说：Attractor 回答的是"无论具体实现怎么变，系统永远不应该失去哪些结构特征"。

例如：

```text
ORM 模型是领域结构的唯一事实来源
```

这不是在规定某个具体类必须怎么写，而是在定义一组长期关系：

- 元数据应从 ORM 模型派生；
- 生成代码不应反过来成为新的独立事实来源；
- 查询、验证、工具链和文档应围绕同一模型收敛；
- 临时绕过不能逐渐形成第二套模型体系。

某次直接使用 JDBC 的补丁可能：

- 能够编译；
- 测试通过；
- 没有违反显式禁令；
- 在当前需求下完全可用。

但如果这种变更不断累积，系统会逐渐远离“ORM 模型唯一事实来源”这一长期结构。

边界只能告诉我们某次操作是否越界；Attractor 还要告诉我们多次操作累积后，系统正在靠近还是远离某种稳定结构。

## Attractor 的三层结构

为了避免把 Attractor 等同于文档，可以将其分成三层。

### 1. 结构层：Attractor 本身

由少量高价值不变量构成，例如：

- 核心原语的闭集；
- 模块责任的划分；
- 依赖方向；
- 数据与能力的正交关系；
- Template 与 Instance 的分离；
- 聚合根对业务行为的所有权；
- 单一事实来源。

### 2. 载体层：Owner Docs

这些不变量必须被外化到：

- 可版本化；
- 有明确 owner；
- 有优先级；
- 可被 AI 路由和加载；
- 可被审计和更新；

的仓库文档中。

文档不是 Attractor 本身，而是 Attractor 的工程载体。

### 3. 实现层：当前代码投影

当前代码是 Attractor 在某一时刻的实现投影。它可能：

- 完整体现 Attractor；
- 部分体现；
- 暂时偏离；
- 暴露出 Attractor 本身需要调整。

因此，代码和架构文档并不是在争夺同一种权威：

- 问当前系统实际怎么运行，代码是事实；
- 问系统长期应该向哪里收敛，Owner Docs 是方向基线；
- 问为什么放弃某条路径，日志、Bug 和分析记录是历史事实。

### nop-app-erp 中的三个具体 Attractor

以正在开发的 nop-app-erp 为例，三个贯穿全部 22 天开发的结构不变量可以说明 Attractor 的具象形态：

1. **ORM XML 唯一真相源**（`model/*.orm.xml`）——所有持久化代码从 XML 生成，手写绕过直接导致编译失败。这不只是"代码规范"，而是定义了"元数据从哪来、生成代码和源模型的关系"这一组长期关系。
2. **DAG + R/S/P 跨域契约**——模块依赖为无环有向图，跨域引用严格分为三类：只读桩（Reader）、同步接口（Service）、弱关联字符串（Path）。369 条白名单使每个跨域引用都经过显式声明，不会在多次变更中逐渐缠绕成网状依赖。
3. **三轴正交状态分离**（`docStatus × approveStatus × posted`）——业务单据的三个状态维度彼此独立、互不污染。一次 PR 可能只修改了审批流，如果审核状态和过账状态被连带耦合，审计就会发现偏离。

这三个 Attractor 不是一开始就明确的：它们在开发过程中逐渐被识别、外化到 Owner Docs，然后被 Plan Loop 的审查者和 Mission Driver 的审计步骤反复引用。它们本身也不"完成"——当新的事实（比如跨域红冲需求）出现时，它们需要被修正，但不能被无成本修改。

## 五、Attractor 不是什么

## 1. Attractor 不是 Roadmap

Roadmap 说明：

> 接下来做哪些工作。

Attractor 说明：

> 无论做哪些工作，系统长期应保持什么结构关系。

Roadmap 可以完成，Attractor 通常不会“完成”。它持续作用于后续演化。

## 2. Attractor 不是 Spec

Spec 主要描述：

> 某项能力应表现出什么行为。

Attractor 关注：

> 大量能力持续加入后，系统仍应保持什么结构同一性。

Spec 可以成为局部 Harness，也可以表达部分不变量，但它不自动承担整个系统的长期收敛方向。

## 3. Attractor 不是 Guardrail

Guardrail 主要判断：

> 当前动作是否允许。

Attractor 主要判断：

> 连续动作累积后，整体结构是否仍在靠近稳定区域。

十次 PR 都可能通过 Guardrail，却共同形成架构漂移。

## 4. Attractor 不是架构终态

终态思维是：

> 设计一个 X，然后到达 X。

Attractor 思维是：

> 系统会持续受到需求、AI 生成、重构和外部反馈的扰动；关键不是永远停在 X，而是偏离后仍能回到由 X 所代表的结构附近。

它关注的是**扰动下的稳定性**。

## 5. Attractor 不是文档数量

大量文档不会自动形成 Attractor。

如果文档没有：

- 明确责任；
- 权威优先级；
- 与代码和计划的同步机制；
- 冲突裁决；
- 更新证据；
- 审计入口；

那么它们只是另一组可能漂移的文本。

### 五种"不是"的小结

| 混淆对象 | 核心区别 |
|---------|---------|
| Roadmap | 说明"接下来做什么"；Attractor 说明"无论做什么，系统长期应保持什么结构" |
| Spec | 描述"某项能力应表现什么行为"；Attractor 关注"大量能力加入后仍保持什么结构同一性" |
| Guardrail | 判断"当前动作是否允许"；Attractor 判断"连续动作累积后是否仍靠近稳定区域" |
| 架构终态 | 终态是"设计 X → 到达 X"；Attractor 是"偏离 X 后仍能回到 X 附近" |
| 文档数量 | 文档堆砌不自动形成 Attractor；缺少责任、优先级和同步机制就是另一组可能漂移的文本 |

## 六、为什么是“State Space → Attractor → Trajectory → Control”

这个顺序不是 Mission Driver 的执行顺序，而是评价逻辑的依赖顺序。

## State Space：系统可能变成什么

系统并不是在一个空白空间中任意变化。技术栈、平台能力、已有代码、测试、文档、领域规则和组织权限——这些共同构成了仓库的完整状态空间，限定了系统可能演化出的状态集合。

状态空间在 AGE 中具有基础性地位：没有它，就无法定义 Attractor 是在"哪些可能状态中"识别稳定结构；没有它，Trajectory 就失去了"在哪条路径上移动"的坐标；没有它，Control 也无法判断偏离发生在哪个维度。

状态空间不是静态的——当引入新框架、新领域、新工具时，它本身也在扩张。但它不能模糊到"什么都可以"的程度：如果状态空间没有边界，那么任何轨迹变化都可以被重新解释为合法演化。

## Attractor：哪些长期结构值得维持

在可能状态中，需要先识别什么样的结构应当长期稳定存在。

如果没有 Attractor，就无法区分：

- 合法演化；
- 临时偏离；
- 结构漂移；
- 需要改变原有方向的新发现。

## Trajectory：系统实际上怎样走到了这里

单个快照不能解释系统为什么成为现在这样。

Plan、Git 历史、日志、Bug、审计和讨论记录，共同保存：

- 哪些路径被选择；
- 哪些假设被证伪；
- 哪些完成判断后来被推翻；
- 哪些临时结构逐渐固化；
- 哪些新事实促使 Attractor 更新。

## Control：如何持续影响轨迹

测试、Lint、Plan、Review、Audit、Mission Driver 和人工介入，都是控制机制。

但控制不能先于方向获得意义。必须先知道系统应维持什么结构，才能回答：

- 检查什么；
- 什么算偏离；
- 失败后回到哪里；
- 哪些问题不能延期；
- 哪些规则应该被机器化。

因此，“Attractor Before Harness”中的 before 不是瀑布式时间顺序，而是：

> **方向在评价逻辑上先于控制。**

运行过程中，两者当然共同演化：

```text
定义 Attractor
→ Harness 推动扩张
→ 实践暴露矛盾
→ 修正 Attractor
→ 更新 Harness
→ 继续扩张
```

## 七、Mission Driver 在 AGE 中的准确位置

Mission Driver 不是定义方向的系统。

它是 Harness 层的自动控制实现，负责：

- 读取当前仓库状态；
- 审查 Plan；
- 执行 Plan；
- 验证关闭条件；
- 起草下一批 Plan；
- 在任务耗尽时启动深度审计；
- 将发现的问题重新送入执行循环。

它解决的是：

> 当方向已经被外化后，如何让控制过程脱离人的同步参与，并持续运行。

因此，Mission Driver 的五步循环不应被理解为 AGE 本身：

```text
CHECK
→ REVIEW_PLANS
→ EXEC_PLANS
→ DRAFT_PLANS
→ DEEP_AUDIT
```

这些步骤是否有意义，取决于它们在读取什么方向：

- REVIEW 根据什么判断 Plan 是否合理？
- EXEC 根据什么选择实现结构？
- CLOSURE_AUDIT 根据什么判断完成？
- DEEP_AUDIT 根据什么识别系统性偏离？
- DRAFT 根据什么把 Roadmap 投影为下一轮工作？

如果答案只是“根据当前代码和现有测试”，那么 Mission Driver 可能只是高效复制当前基线。

如果当前基线本身已经偏离，它会更快地固化错误。

所以：

> Mission Driver 能保证 Loop 持续推进，但不能单独保证轨迹方向正确。

---

## 八、Plan 不是任务列表，而是局部轨迹的关闭契约

在这个体系中，Plan 的核心价值不是帮助 AI 记住待办事项，而是定义：

> 当前这一轮局部扩张，必须在哪些条件下闭合，才能重新成为可接受轨迹的一部分。

因此，一个 Plan 需要包含：

- **Current Baseline**：不是想象中的起点，而是 live repository 的真实状态；
- **Goals**：本轮要改变什么；
- **Non-Goals**：哪些邻近范围不允许被顺手扩张；
- **Execution Items**：实际修改；
- **Proof Items**：证明修改真的成立；
- **Exit Criteria**：Phase 如何结束；
- **Closure Gates**：整个 Plan 如何关闭；
- **Owner-Doc Adjudication**：是否改变长期方向基线；
- **Independent Audit Evidence**：由不同上下文重新判断完成。

普通任务列表关注：

> 做了什么？

Plan 关注：

> 当前轨迹必须在哪里结束，哪些证据足以证明它确实结束在这里？

Checkbox 本身不是证明。它只是执行状态。真正的证明仍然来自：

- 当前代码；
- 可执行测试；
- 静态检查；
- Owner Docs；
- 运行证据；
- 独立审计。

## 九、为什么“生成与验收分离”仍然不够，但不可缺少

AI 可以在同一个上下文中生成：

- 实现；
- 测试；
- 文档；
- 完成说明；
- 自我审查结论。

如果最初理解错误，这些材料可能在同一方向上保持一致。它们不会互相矛盾，却可能共同偏离真实需求或长期结构。

一个具体的例子：假设 AI 错误地将某个跨模块的共享值对象识别为"各模块独立维护的枚举"，那么它会在这个理解下生成代码、测试（为每个模块重复编写相同的验证逻辑）、文档（在各模块文档中分别描述这个"枚举"的取值含义）、自我审查结论（"所有模块均独立覆盖了该枚举的完整取值"）——所有产出都自洽，但共同指向一个错误的架构方向：事实来源正在分裂。

Fresh Session 和独立子代理的作用不是创造绝对客观性，而是重建最基本的认识分离：

> 验收者不能直接继承生成者“我为什么觉得自己已经完成”的叙事。

验收者必须重新读取 live repository，并从外部证据开始判断。

不过，独立会话不等于最终真理。可靠性仍然需要证据层次：

```text
编译、类型、Lint
→ 单元与集成测试
→ 属性和业务不变量
→ E2E
→ 架构一致性检查
→ 独立语义审计
→ 必要时领域专家或真实用户验证
```

独立 Agent 是 Harness 的组成部分，不应被误解成外部第三方认证。

## 十、“仓库是唯一真相源”不等于“代码是唯一真相”

更准确的说法是：

> 仓库承载了不同类型的系统事实，而不同材料只对相应问题拥有权威。

| 问题 | 主要权威来源 |
|---|---|
| 当前系统实际如何运行 | 代码、配置、运行状态 |
| 当前行为是否成立 | 测试、运行证据、可执行检查 |
| 系统长期向哪里收敛 | Owner Docs |
| 本轮变更如何关闭 | Plan |
| 为什么选择或放弃某条路径 | Logs、Bugs、Discussions、Analysis |
| 当前还有哪些宏观工作 | Roadmap |
| 哪些历史判断已被证伪 | Bug、Audit、Decision Record |

这种责任划分很重要。

如果把所有东西都视为同等权威，AI 会在冲突时随意选择对当前任务最方便的材料。如果把代码视为唯一真相，当前偏离就会被自动升级为未来规范。如果把文档视为唯一真相，又可能无视真实实现。

AGE 要建立的不是“一个文件统治一切”，而是：

> 一个具有责任边界和优先级的仓库事实系统。

---

## 十一、谁来定义和修改 Attractor

Attractor 不能被理解为架构师一次写完、永远不变的圣经。

它需要演化，但不能被无成本修改。否则 AI 每次无法满足架构原则时，都可以通过修改原则来使当前实现合法。

因此需要区分两类变更：

## 轨迹纠偏

实践没有推翻原有结构，只是当前实现发生偏离。

此时应修改代码，而不是修改 Attractor。

## Attractor 修正

新的事实证明：

- 原有边界不可持续；
- 原有概念切分产生系统性矛盾；
- 新需求改变了状态空间；
- 原有不变量阻碍了更高层结构；
- 多次局部修补暴露出方向本身错误。

此时才应更新 Owner Docs，并同步更新：

- Plan Guide；
- 验证规则；
- Audit Prompt；
- 测试与静态检查；
- 后续 Roadmap。

AI 可以提出候选 Attractor，也可以通过审计发现旧结构的矛盾。但高影响方向变更不能默认由提出者自行宣布成立。

更合理的责任关系是：

```text
人和 AI 都可以提出候选方向
→ 通过反例、原型、审计和领域证据竞争
→ 高影响变更由明确 owner 裁决
→ 新方向进入 Owner Docs
→ Harness 被同步更新
```

真正稀缺的不是“谁能想到一个新架构名词”，而是谁能够对结构基线的改变承担责任。

---

## 十二、如何理解“AI 全自动开发”

“全自动”至少有三个不同层次。

## 1. 执行自动化

给定明确 Plan，AI 可以自主：

- 修改代码；
- 编写测试；
- 运行验证；
- 修复失败；
- 提交审计证据。

## 2. 编排自动化

给定 Roadmap 和 Attractor，Mission Driver 可以自主：

- 起草 Plan；
- 审查 Plan；
- 排队执行；
- 关闭任务；
- 发现空档；
- 启动深度审计；
- 生成整改工作。

## 3. 方向自治

系统能够自主：

- 澄清模糊目标；
- 提出新的结构语言；
- 比较竞争性 Attractor；
- 处理真实组织利益冲突；
- 决定产品战略；
- 对方向性错误承担责任。

前两层已经可以达到很高程度的自动化。第三层目前仍然需要明确的人类治理。

因此，nop-app-erp 案例中的“全自动”更准确地应理解为：

> 在方向和关键结构逐渐明确后，执行与编排层进入高自主运行，人从同步执行节点转变为异步方向和异常治理者。

Human On The Loop 不是没有人，而是人的位置发生了变化：

```text
从逐步确认
→ 转向定义方向、权限、预算、风险和升级条件
```

---

## 十三、nop-app-erp 案例究竟说明了什么

nop-app-erp 是一个基于 Nop 平台的 ERP 应用骨架，覆盖 18+1 个业务域、154 个 Maven 模块、352 个自有实体。案例中的模块、实体、测试、Plan 和审计数量，不应被单独理解为 AGE 理论的证明。

它真正提供的证据是：

1. 在长期方向被逐渐外化后，AI 可以承担大规模扩张；
2. Plan Closure 能让复杂变更跨会话持续推进；
3. 文件化状态支持长时间执行和恢复；
4. 独立审计可以反复推翻虚假完成；
5. 人类介入会从具体平台知识纠正，逐渐转向高层方向治理；
6. 当结构基线稳定后，AI 的自主扩张比例明显提高；
7. Mission Driver 可以将上述过程从人工编排变成自动编排。

它没有单独证明：

- 任意领域都能以同样方式全自动开发；
- 当前测试已经等同于真实客户验收；
- Attractor 一经定义就必然正确；
- 所有架构创新都可以自动产生；
- Harness 可以替代产品判断。

案例的意义不是宣称“人已不再重要”，而是显示：

> 当人的方向性知识被迁移到仓库结构后，人的持续同步参与不再是系统推进的必要条件。

---

## 十四、Loop 并不会自动产生智能

“循环即智能”是一种容易被误解的简化表达。

Loop 真正提供的是：

- 反馈；
- 重试；
- 纠偏；
- 记忆；
- 恢复；
- 审计；
- 逐步改进。

如果反馈信号错误，Loop 不会自动发现真理，它只会更稳定地优化错误目标。

因此，一个完整的 AGE 系统至少包含三种不同性质的东西：

```text
Attractor
定义长期结构方向

Harness
测量、控制和纠偏轨迹

Memory
保存事实、历史和被证伪路径
```

Mission Driver 主要属于 Harness。

Plan 同时连接 Harness 与 Memory。

Owner Docs 主要承载 Attractor。

Logs、Bugs、Analysis 和 Git History 保存 Trajectory。

测试、审计和人工反馈提供 Control Signal。

它们不能互相替代。

因此一个合理的追问是：既然 Attractor 需要维护，它会不会成为另一组随时间腐烂的文档？nop-app-erp 的实践经验是：Attractor 的腐烂速度取决于它是否被 Harness 层持续引用。如果 Owner Docs 只在起草时被读一次，之后永远不再被审计步骤检查——它就会腐烂。如果每条 Plan 的审查和结束审计都要求检查 Attractor 一致性——它就不会。关键在于 Attractor 的载体文件是否被纳入了控制循环的输入。

---

## 十五、普通项目真正应该先落地什么

不需要先部署完整 Mission Driver，也不需要立即建立复杂文档体系。最小实践可以从四件事开始。

## 1. 写一份真正的 Owner Doc

不要写代码导览，而要写：

- 核心事实来源；
- 责任边界；
- 依赖方向；
- 状态转换；
- 长期不变量；
- 常见错误理解；
- 哪些旧结构已不再合法。

## 2. 对复杂变更使用 Closure Plan

至少包含：

```text
Current Baseline
Goals
Non-Goals
Execution
Proof
Closure Gates
Owner-Doc Impact
```

## 3. 将生成与验收分离

不要让同一个上下文仅凭自己的完成说明关闭任务。重新读取 live repository，用外部证据判断。

## 4. 保存否定知识

不仅记录“最后怎么做”，还要记录：

- 哪个前提已经被证明错误；
- 哪种实现虽然能跑但会导致结构漂移；
- 哪个完成判断后来被推翻；
- 哪种测试写法会掩盖真实失败。

这四件事的共同特点是：它们不依赖 Mission Driver 或任何特殊的工具链。只用 Markdown 文件、git 仓库和独立的 AI 会话就能开始。当四件事稳定后，再引入 Mission Driver 自动编排，收益会更大。方向已经外化到了文件中，剩下的就是把控制过程也自动化。

否则只是把尚未形成方向的流程自动化。

## 十六、最终澄清

Mission Driver、Loop Engineering 和 Attractor-Guided Engineering 不是三个并列的品牌名词，而是三个不同层次的问题。

## Mission Driver 回答

> 如何自动推进一个长期任务？

## Loop Engineering 回答

> 如何用反馈、重试、隔离、恢复和验证组织概率性的 AI 执行？

## Attractor-Guided Engineering 回答

> 如何让大量局部正确的 AI 变更，在长期演化中仍然保持结构方向，并在偏离后能够被重新拉回？

三者之间的关系可以压缩为：

```text
Attractor 定义长期结构
Trajectory 记录实际演化
Plan 关闭局部轨迹
Harness 提供测量和纠偏
Mission Driver 自动编排 Harness
Repository 承载跨会话事实与记忆
```

最需要澄清的一句话是：

> **AGE 的核心不是让 AI 更严格地完成任务，而是把过去由人类连续认知隐式承担的系统方向性，外化为可继承、可审计、可纠偏的仓库结构。**

因此，Attractor Before Harness 不是说文档比代码重要，也不是说架构必须预先设计完成。

它真正表达的是：

> 在决定如何约束、验证和循环之前，必须先回答系统应长期保持什么结构；否则，越稳定的 Harness，越可能只是把错误方向执行得更快、更彻底。
