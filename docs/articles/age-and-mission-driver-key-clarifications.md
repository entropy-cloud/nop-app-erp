# 吸引子引导工程（AGE）与 Mission Driver 的关键澄清  

> Mission Driver 解决的是控制循环如何持续运行；AGE 解决的是这些循环应当把项目带向哪里，以及项目如何在开发主体不连续的条件下仍然保持结构同一性。  
> 二者的关系不是“理论与工具”的简单对应，而是“方向、状态、轨迹、控制与持续编排”之间的层次关系。

关于 Attractor-Guided Engineering（AGE）与 Mission Driver，许多误解表面上是术语混淆，根源却是仍在沿用传统软件工程的隐含前提：

> 项目的长期方向可以继续由少数长期参与者在头脑中维持。

在这个前提下，代码、测试、文档和流程只需支持人的工作。即使它们之间存在冲突、遗漏和过期，长期参与者也能依靠记忆和经验进行补偿：

- 知道哪段现存代码不应继续模仿；
- 知道哪份文档已经失效；
- 知道某个测试只是旧实现的遗留；
- 知道某种临时结构不能成为长期基线；
- 知道最近多个局部变更正在形成什么趋势；
- 知道哪些失败路径已经被证伪。

AI 深度参与开发之后，这个隐含前提不再成立。

AI 可以高频、大幅度地修改多个模块，却没有天然的跨会话方向连续性；它还可以在同一理解下同时生成代码、测试、文档、Plan 和完成说明。每项产出单独看都可能合理，彼此之间也可以高度一致，但整个项目仍可能沿错误方向持续演化。

因此，AGE 首先不是一种“约束 AI 的方法”，而是对一个更基础问题的回答：

> 当开发主体不再连续时，项目本身如何获得连续性？

理解这一点，才能准确区分 Attractor、Harness、Loop Engineering 与 Mission Driver。

---

# 一、AGE 改变的首先是工程评价对象

传统软件工程主要围绕当前状态进行评价：

- 当前代码能否编译；
- 当前测试是否通过；
- 当前需求是否实现；
- 当前 PR 是否符合规范；
- 当前 Plan 是否满足关闭条件。

这些检查不可缺少，但它们不能独立回答：

> 连续一百次局部正确的变更，正在把系统推向什么结构？

项目可能出现这样的情况：

```text
每次提交都能编译
每个测试都通过
每项需求都已经实现
每个 Plan 都能关闭
每次 Review 都没有发现明显问题
```

与此同时：

```text
模块责任正在重叠
单一事实来源正在分裂
测试正在与旧实现细节耦合
临时兼容层正在变成永久结构
同一领域概念正在产生多套表达
当前代码正在无声取代长期设计基线
```

这里未必存在某一个可以单独定位的错误提交。问题产生于一系列合法状态之间的累积关系。

因此，AGE 将软件工程的基础评价对象从单一状态扩展为：

```text
状态
+ 状态之间形成的轨迹
+ 轨迹长期趋向的结构
+ 影响轨迹的控制机制
```

这不是“把历史也纳入 Review”，而是承认：

> 一个状态是否可接受，不只取决于它现在能否工作，还取决于它在什么轨迹中、承担什么后续义务，以及是否仍然具有回归长期结构的能力。

# 二、必须区分期望吸引子与实际吸引子

关于 Attractor，最容易产生的混淆，是把“系统应该收敛到哪里”和“系统实际上会收敛到哪里”视为同一个问题。

二者必须明确区分。

## 1. 期望吸引子：项目选择维持的长期结构

期望吸引子回答：

> 系统在持续演化中，应该反复保持或重新回到什么结构附近？

它由少量高价值的结构关系定义，例如：

- 某个模型是领域事实的唯一来源；
- Template 与 Instance 必须分离；
- Data 与 Capability 必须正交；
- 模块必须遵守明确的依赖方向；
- 核心原语形成闭集；
- 聚合根拥有业务行为；
- 生成代码不能反过来成为独立事实来源。

期望吸引子不是一个完整的未来版本，也不是所有合法代码的清单。它规定的是项目在变化中仍然保持自身身份所依赖的结构关系。

它允许：

- 新需求；
- 新实现；
- 局部重构；
- 实验性探索；
- 暂时适配；
- 受控迁移；
- 对自身结构的重新裁决。

但这些变化不能在缺少裁决的情况下，无声改变项目的组织同一性。

期望吸引子通常由 Owner Docs 承载，但 Owner Docs 不是吸引子本身。文档只是把这些结构关系变成可版本化、可路由、可审计和可修改的工程表示。

## 2. 实际吸引子：现有演化机制真正反复生成的结构

实际吸引子回答的是另一个问题：

> 在当前代码基线、开发习惯、测试、CI、Plan、Review、Agent 行为和组织激励共同作用下，项目实际上会反复回到什么结构？

实际吸引子不是当前代码。

当前代码只是状态空间中的一个状态；实际吸引子是一种通过长期轨迹才能识别的演化倾向。

例如，Owner Docs 可能规定：

```text
领域模型必须拥有唯一事实来源
```

但实际开发中，如果：

- 各模块复制模型最方便；
- 测试只验证模块内部自洽；
- Review 不检查跨模块语义重复；
- 计划按局部功能关闭；
- 复制产生的成本被推迟到未来；

那么项目的实际吸引结构可能是：

```text
每个模块都维护一套局部模型
```

同样，架构文档可能规定：

```text
临时适配层必须在迁移后删除
```

但如果适配层没有 Owner、退出条件和 Closure Gate，后续变更不断在其上继续扩展，那么“永久兼容层”就可能成为实际吸引子。

实际吸引子不一定是被设计出来的，也不一定是好的。它可能由以下因素共同产生：

- 当前代码提供的模仿基线；
- 最容易通过测试的实现方式；
- 局部交付压力；
- 缺少退出义务的临时方案；
- 过时但仍有权威外观的文档；
- 与实现细节耦合的测试；
- 持续奖励局部完成的任务结构。

## 3. AGE 的目标是让二者逐步对齐

AGE 不是假定“写下期望结构之后，系统就拥有了吸引子”。

仅仅写入 Owner Docs 的结构，首先只是一个被正式选择的规范基线。它要成为工程上有效的吸引子，还必须被投影到：

- 信息路由；
- Owner；
- Precedence；
- Proof Relation；
- Plan 义务；
- Closure Gate；
- Audit；
- Freshness；
- 自动检查；
- 异常升级规则。

随后，这些关系还必须实际影响后续变更。

因此，可以把 AGE 的目标表示为：

```text
定义期望吸引子
→ 将其外化为仓库语义结构
→ 根据它设计 Harness
→ Harness 改变实际演化规则
→ 观察长期轨迹
→ 判断实际吸引子是否接近期望吸引子
→ 修正实现、Harness 或期望吸引子
```

这里有三个不能混淆的对象：

| 对象 | 含义 |
|---|---|
| 当前状态 | 项目此刻实际是什么 |
| 期望吸引子 | 项目选择长期保持什么结构 |
| 实际吸引子 | 当前演化机制事实上反复产生什么结构 |

当前状态符合 Owner Docs，不足以证明实际吸引子已经对齐。一次检查通过只说明当前截面没有暴露问题；只有经过持续扰动、偏离和纠偏之后，系统仍能反复恢复关键结构，才能说明期望吸引子正在成为有效的工程吸引子。

# 三、“Attractor Before Harness”究竟是什么意思

区分期望吸引子和实际吸引子之后，`Attractor Before Harness` 的含义就更加清楚。

它不是说：

```text
先设计完全部架构
→ 冻结长期结构
→ 再实现测试和控制机制
```

也不是说实际吸引子可以脱离 Harness 独立产生。

这里的 `Before` 指评价逻辑上的优先关系：

> 必须先定义希望维持的长期结构，才能决定 Harness 应当测量什么、拒绝什么、允许什么以及把偏离拉回哪里。

没有期望吸引子，无法稳定回答：

- 哪种重复是合理局部自治，哪种是事实来源分裂；
- 哪个测试是在证明行为，哪个测试是在固化旧实现；
- 哪种临时旁路可以接受，哪种已经形成结构漂移；
- Plan 应该在哪里关闭；
- Audit 应该寻找什么；
- Mission Driver 应该依据什么生成后续工作。

但从实际动力学看，Harness 又是把期望吸引子转化为真实回归能力的必要条件。

因此，完整关系不是单向的：

```text
期望吸引子在评价逻辑上先于 Harness
Harness 将期望结构投影为实际控制
实际轨迹暴露二者是否对齐
长期证据反过来修正 Harness 或期望吸引子
```

简化地说：

> 期望方向先于控制设计；实际吸引力形成于方向、仓库状态、控制机制和开发行为的共同作用。

这并不削弱 `Attractor Before Harness`，而是避免把“规范方向”与“实际动力学结果”混为一谈。

---

# 四、Attractor 不是架构终态，也不只是架构原则

将 Attractor 理解为“架构原则”仍然不够。

架构原则通常用于判断：

> 当前实现是否满足某条规则？

Attractor 还要求判断：

> 系统在被扰动之后，是否仍然能够重新回到由这些关系定义的稳定区域？

这引入了传统静态合规不容易表达的三个方面。

## 1. 中间状态可以暂时偏离

复杂演化可能需要：

- 双写；
- 兼容层；
- 过渡接口；
- 临时数据模型；
- 未完成的包拆分；
- 用于验证假设的原型。

AGE 不要求每个中间状态都成为最终结构的完美投影。

## 2. 暂时偏离不能自动获得长期合法性

一个中间状态必须能够说明：

- 为什么出现；
- 由谁负责；
- 允许存在多久；
- 哪些范围不得继续扩张；
- 什么条件下退出；
- 用什么证据证明已经退出；
- 是否改变长期结构基线。

如果这些信息不存在，下一个开发主体只能把当前仓库视为正常基线。临时结构就会在没有任何正式裁决的情况下，被后续变更不断继承。

## 3. 关键是回归能力，而不是瞬时完美

真正需要评价的是：

- 系统是否知道自己发生了偏离；
- 偏离是否被记录为未关闭义务；
- 后续工作是否会继续推动回归；
- Harness 是否能够发现偏离正在沉淀；
- 当前结构是否仍在期望吸引子的可回归范围内。

因此，Attractor 关注的不是静态纯洁性，而是扰动下的结构稳定性。

# 五、AGE 不是更多文档，而是仓库语义权威结构

将方向写进文档，并不会自动解决问题。

仓库中通常同时存在：

- 当前源码；
- 架构说明；
- 历史分析；
- 活跃 Plan；
- 旧 Plan；
- 测试；
- Bug 记录；
- 审计结论；
- 迁移说明；
- 已失效的讨论。

如果这些材料没有明确的责任边界和优先级，AI 面对的不是知识丰富，而是多个竞争性真相源。

AGE 因此要求建立的不是文档集合，而是语义权威拓扑：

```text
领域概念
→ 语义承诺
→ Owner
→ 当前实现
→ 证明证据
→ 变更计划
→ 审计裁决
→ 轨迹记忆
→ 后续义务
```

其中至少包含几类关系。

## Owner

谁拥有某项语义或结构定义？

## Precedence

代码、文档、Plan、测试和历史分析冲突时，针对当前问题应以什么为准？

## Proof

哪项测试或运行证据在证明哪条语义承诺？

## Freshness

某份材料是否仍足以支持后续自主行动？

## Closure

本轮变化还有哪些义务没有关闭？

## Trajectory Memory

哪些历史结论仍然约束未来，哪些路径已经被证伪？

因此，“仓库是真相源”不是“代码是真相”，也不是“Owner Docs 比代码更权威”。

不同材料只对不同问题拥有权威：

| 问题 | 主要权威 |
|---|---|
| 当前系统实际怎样运行 | 代码、配置、运行状态 |
| 某项行为是否成立 | 测试与运行证据 |
| 系统长期应维持什么结构 | Owner Docs |
| 本轮变化承担什么义务 | Plan |
| 是否满足关闭条件 | Closure Evidence 与独立 Audit |
| 为什么选择或放弃某条路径 | Logs、Bugs、Analysis、Discussions |
| 某条历史判断是否已经失效 | 后续 Audit、Bug 或正式裁决 |

AGE 的目标不是选出一个文件统治所有问题，而是让权威归属本身成为可恢复的项目状态。

# 六、状态空间不是源码空间

如果项目状态只指源码快照，那么两个源码完全相同的仓库就应当处于同一工程状态。

实际上并非如此。

假设两个仓库都包含同一个双写适配层。

第一个仓库明确记录：

- 它是迁移中的临时结构；
- 由哪个 Plan 引入；
- 哪些模块尚未迁移；
- 何时必须删除；
- 哪个测试证明最终单写结构；
- 谁负责关闭。

第二个仓库没有任何相关记录。后续主体只能把双写理解为正式设计。

两个仓库的源码相同，但后续可接受的行动不同：

- 第一个仓库要求继续完成迁移；
- 第二个仓库可能继续围绕双写结构扩张。

因此，完整工程状态不只包括代码，还包括会影响后续理解、判断和行动的内容：

- Owner Docs；
- Tests；
- Schemas；
- Plans；
- Logs；
- Bugs；
- Audits；
- 决策与否定知识；
- 未关闭义务；
- 权威与证明关系；
- 当前材料的新鲜度。

“完整”并不意味着把生产数据库、客户组织和全部外部现实复制进仓库，而是要求：

> 所有已经影响项目方向和后续判断的重要外部事实，都应在仓库中留下可恢复、可版本化或可引用的工程表示。

# 七、Trajectory 不是 Git 历史

Git 历史保存了文件如何变化，却不会自动保存这些变化对未来意味着什么。

它可以回答：

- 哪些行被修改；
- 哪个提交引入某个文件；
- 某段代码何时出现。

但它不一定能直接回答：

- 当时依赖了什么前提；
- 哪个前提后来被证伪；
- 哪种实现虽然可运行，却不应再次进入；
- 哪个完成结论后来被 live repository 推翻；
- 哪个临时结构正在获得长期合法性；
- 哪次实践促使期望吸引子发生修正。

AGE 所说的轨迹记忆，是从历史事件中提炼出对未来仍然有效的语义约束。

可以概括为：

```text
Git 保存“发生过什么”
Trajectory Memory 保存“这些事情对未来意味着什么”
```

这也是 Logs、Bugs、Audits、Analysis 和 Discussions 的真正作用。它们不是过程附件，而是跨会话传递方向性认识的结构记忆。

当然，轨迹记忆也不能无限累积。已失效、已被提炼或已被替代的材料必须能够归档和降权。否则历史记录本身也会成为新的漂移源。

# 八、Plan 不是任务列表，而是对中间状态合法性的管理

普通任务列表回答：

> 要做哪些事情？

Closure Plan 回答：

> 这一段局部轨迹从哪里开始，允许发生什么变化，必须在哪里闭合，以及什么证据足以证明闭合。

这个区别在跨会话开发中尤其重要。

一次迁移进行到一半时，仓库可能同时存在：

- 旧接口；
- 新接口；
- 兼容层；
- 临时测试；
- 部分迁移模块；
- 过渡文档。

原执行者知道这些是中间状态，但下一个 Session 只能读取当前仓库。如果没有显式 Plan，它很可能把这些临时结构理解成正式架构。

于是，中间状态无需经过任何裁决，就能通过后续扩张逐渐获得长期合法性。

Closure Plan 正是为了阻止这种无声升级。它至少需要说明：

- **Current Baseline**：真实起点是什么；
- **Goals**：本轮要改变什么；
- **Non-Goals**：哪些邻近范围不得顺手扩张；
- **Execution Items**：需要实施什么；
- **Proof Items**：必须重新证明哪些承诺；
- **Exit Criteria**：阶段怎样结束；
- **Closure Gates**：整个 Plan 怎样关闭；
- **Owner-Doc Impact**：是否改变期望吸引子；
- **Independent Audit Evidence**：完成是否经过独立重判。

Plan 的核心不是管理工作量，而是规定：

> 当前仓库中的哪些现实仍然只是过渡状态，尚未获得成为长期基线的资格。

# 九、测试不是天然的 Proof，Harness 也不是天然正确的裁判

测试通过不等于语义承诺已经被证明。

测试只有在与某项承诺保持有效关系时，才构成 Proof。

例如，系统的真实承诺是：

```text
Spreadsheet 在任意数据规模下正确呈现当前可见行
```

旧实现一次挂载全部行，因此测试写成：

```text
断言 30 个 row headers 同时存在
```

当实现改为虚拟化后，这个测试可能仍然稳定、清晰，却已经不再证明原始行为。它开始保护旧实现细节。

这就是 Proof Drift：

```text
测试仍然存在
测试可能仍然通过
但测试与原始语义承诺之间的证明关系已经断裂
```

因此，AGE 要维护的不是简单的：

```text
代码 ↔ 测试
```

而是：

```text
语义承诺
→ 可观察后果
→ 证明证据
```

这也意味着 Harness 自身必须被审计。

当测试、Lint、Review 或 Audit 保护了错误对象时，Harness 越稳定，错误结构越难改变。更慢的 Loop 必须能够判断：

- 是实现错了；
- 是 Plan 前提错了；
- 是测试测错了对象；
- 是 Audit 依据已经过期；
- 还是期望吸引子本身需要修正。

AGE 不是简单加强 Harness，而是把 Harness 也放回可检查、可纠偏的长期轨迹中。

---

# 十、生成与验收分离不是重复检查，而是重建认识独立性

AI 可以在同一个上下文中生成：

- 代码；
- 测试；
- 文档；
- Plan 更新；
- 完成说明；
- 自我审查结论。

如果最初理解发生偏差，这些产出可以彼此一致，却共同指向错误方向。

因此，Fresh Session 和独立 Audit 的意义不是“再看一遍”，而是切断验收对生成者完成叙事的直接继承。

验收者必须重新读取：

- live repository；
- 当前 Owner Docs；
- Plan 义务；
- Proof Evidence；
- 未关闭冲突；
- 当前材料的新鲜度。

Fresh Session 仍然不是绝对客观的第三方。相同模型、相同资料和相似 Prompt 仍可能产生相关错误。所以可靠性还需要来自：

- 可执行检查；
- 属性测试；
- 变异测试；
- E2E；
- 真实运行证据；
- 不同模型或不同工具；
- 领域专家；
- 用户反馈。

独立 Audit 的作用是恢复认识分离，不是宣布绝对真理。

---

# 十一、AGE 不能被降级为 Agent Skill

Skill 的组织方式是：

```text
任务意图
→ 匹配能力包
→ 加载执行程序
```

它适合回答：

> 遇到这类任务时，应该采用什么方法？

AGE 维护的却是：

```text
领域概念
→ 语义承诺
→ Owner
→ 实现位置
→ Proof
→ Precedence
→ Freshness
→ 轨迹记忆
→ 后续义务
```

它回答：

- 当前任务在这个项目中究竟意味着什么；
- 哪份材料拥有定义权；
- 哪个测试有资格成为证明；
- 哪些信息已经过期；
- 哪个历史结论仍然约束当前变化；
- 当前变化是否需要修改期望吸引子。

Skill 是在既定语义世界中执行任务的方法；AGE 是构成这个语义世界的持久关系。

因此，可以存在：

- Bug Diagnosis Skill；
- Closure Audit Skill；
- Owner Doc 检查 Skill；
- Proof Drift 检查 Skill。

但不存在一个能够替代仓库语义结构的 `age-skill`。

判断是否发生了过度 Skill 化，可以问：

> 删除所有 Skills 后，仓库是否仍然知道什么是正确的、谁拥有它、如何证明它？

如果答案是否定的，项目的结构身份就被错误地外包给了过程能力包。

---

# 十二、Mission Driver 不是 AGE，也不只是普通工作流引擎

Mission Driver 最容易被理解成自动化 Agent 编排器。

这个理解只看到它的执行形式，没有看到它所承担的连续性功能。

普通工作流引擎通常编排预先确定的步骤：

```text
输入任务
→ 执行步骤
→ 判断成功或失败
→ 进入下一阶段
```

Mission Driver 面对的却是一个会持续改变自身事实、计划、证据和控制条件的仓库。它需要反复完成：

- 从 live repository 恢复当前状态；
- 审查 Plan 是否仍以真实基线为起点；
- 执行并验证 Plan；
- 判断 Closure Gates 是否真正满足；
- 在任务耗尽时起草后续 Plan；
- 发起独立深度审计；
- 用审计结果推翻虚假完成；
- 将新发现重新写入仓库；
- 在进程或 Session 结束后继续运行。

因此，Mission Driver 的准确位置是：

> 它是 Harness 与多层 Loop 的持续编排器，也是仓库化项目连续性的执行机器。

它不是方向来源。它不会凭自身定义：

- 项目应该成为什么；
- 哪份 Owner Doc 有权修改结构基线；
- 哪个 Proof Relation 才是正确的；
- 某个偏离应当修实现还是修正 Attractor。

如果这些关系尚未外化，Mission Driver 只能持续制造文件变化，不能保证这些变化属于同一条可接受轨迹。

---

# 十三、Mission Driver 也是对 AGE 完整性的压力测试

虽然 Mission Driver 不是 AGE 的理论起点，它却能快速暴露 AGE 是否真正落地。

在人工协作中，许多缺口可以被人的临时解释掩盖：

- 文档冲突时，人知道该听谁的；
- Plan 不完整时，人会口头补充；
- 测试过时时，人知道暂时忽略；
- 中间状态未记录时，人记得后续清理；
- Owner 不明确时，架构师可以现场裁决。

Mission Driver 持续运行后，这些隐性补丁会消失。系统会暴露：

- 路由不完整；
- Owner 不明确；
- Precedence 无法裁决；
- Plan 与 live repo 基线不符；
- Closure 只是 Checkbox；
- Proof 与语义承诺脱节；
- 历史材料被误当成当前规范；
- 临时结构没有退出义务；
- Freshness 不足却仍允许自动扩张。

因此，Mission Driver 不只是提高效率。它还在检验：

> 项目是否已经将足够多的方向、权威、证明和轨迹记忆外化，使其不再依赖某个同步在场的人进行解释。

如果答案是否定的，Mission Driver 越自动，漂移可能越快。

---

# 十四、Mission Driver 与实际吸引子的关系

Mission Driver 不定义期望吸引子，但它会显著影响实际吸引子。

原因在于，它决定哪些行为会被反复执行：

- 哪类 Plan 会被优先处理；
- 哪些证据足以关闭任务；
- 何时启动深度审计；
- 哪类问题会被重新送回执行队列；
- 哪些未关闭义务能够跨会话持续存在；
- 哪些失败会触发升级而不是自动修补。

如果 Mission Driver 只奖励：

```text
测试通过
+ Checkbox 完成
+ 当前任务关闭
```

那么它可能把项目拉向“局部完成最大化”的实际吸引子。

如果它持续读取：

- Owner Docs；
- Proof Relation；
- Closure Gates；
- Freshness；
- Independent Audit；
- 未关闭的轨迹义务；

那么它才可能帮助实际吸引子逐渐接近期望吸引子。

因此，Mission Driver 不是中性的执行器。它虽然不拥有方向定义权，却会通过反复编排控制机制，改变项目的真实演化动力学。

这也意味着 Mission Driver 自身必须接受 Meta-Audit：

- 它是否长期偏好容易关闭的任务；
- 它是否忽略难以自动证明的结构问题；
- 它是否把当前测试误当成最终标准；
- 它是否不断复制当前基线；
- 它是否能够识别 Harness Drift；
- 它是否在信息不新鲜时降低自主度。

---

# 十五、期望吸引子也不能成为不可修改的圣经

区分期望吸引子和实际吸引子，并不意味着前者永远正确、后者只需被纠正。

长期实践可能暴露：

- 原有边界不可持续；
- 核心概念切分错误；
- 新需求改变了状态空间；
- 多次局部修补都指向同一结构矛盾；
- Harness 反复失败不是因为实现错误，而是因为原方向无法成立。

此时需要区分两种情况。

## 轨迹纠偏

期望吸引子仍然成立，只是当前实现或控制机制发生偏离。

此时应修改：

- 代码；
- 测试；
- Plan；
- Harness；
- 过期文档；
- Mission Driver 的编排规则。

## 吸引子修正

新的事实表明原有长期结构不再适用。

此时需要：

- 提出反例和替代方案；
- 做原型验证与影响分析；
- 由明确 Owner 裁决；
- 更新 Owner Docs；
- 同步更新 Proof、Plan Guide、Audit 规则和 Roadmap；
- 重新审查现有轨迹义务。

当前实现者不能因为实现困难，就自行修改期望吸引子，使当前结果自动合法化。

AI 可以提出候选、构造反例、分析影响，却不能默认拥有宣布共同结构基线已经改变的权力。

---

# 十六、AGE、Loop Engineering 与 Mission Driver 的准确关系

三者处理的是不同层次的问题。

## AGE 回答

> 项目在长期变化中应保持什么结构，如何判断轨迹漂移，以及如何维持跨会话的组织同一性？

## Loop Engineering 回答

> 如何用反馈、重试、隔离、恢复、验证和多时间尺度闭环，组织概率性的执行过程？

## Mission Driver 回答

> 如何让这些控制机制脱离人的同步参与，在多个 Plan、进程和 Session 之间持续运行？

完整关系可以表示为：

```text
期望吸引子
定义长期结构身份

仓库语义权威拓扑
承载 Owner、Precedence、Proof、Freshness 和轨迹记忆

Plan
定义局部轨迹的允许范围与关闭条件

Harness
将部分方向关系转化为测量、验证和纠偏

Loop Engineering
组织不同时间尺度的反馈与恢复

Mission Driver
持续编排这些 Harness 和 Loop

实际轨迹
暴露项目事实上怎样演化

实际吸引子
由长期轨迹显示项目事实上反复趋向什么结构

Meta-Loop
比较实际吸引子与期望吸引子，并修正实现、Harness 或方向
```

这不是一条只向前运行的流水线，而是递归闭环：

```text
定义期望吸引子
→ 推进项目
→ 观察实际轨迹
→ 识别实际吸引结构
→ 判断偏差来源
→ 修正实现、控制或期望方向
→ 进入下一轮演化
```

---

# 十七、最需要避免的几种降级理解

围绕 AGE 和 Mission Driver 的常见误解，可以归结为几种层级降级。

## 将 Attractor 降级为架构原则

丢失的是扰动、轨迹和回归能力。

## 将 Attractor 降级为 Guardrail

丢失的是多次合法动作累积后的结构趋势。

## 将实际吸引子等同于当前代码

丢失的是吸引子作为长期演化倾向的含义。

## 将 Owner Docs 降级为架构说明书

丢失的是语义权威、Precedence 和方向裁决。

## 将 Trajectory 降级为 Git 历史

丢失的是历史对未来仍然有效的语义约束。

## 将 Plan 降级为任务列表

丢失的是对中间状态合法性和局部轨迹闭合的管理。

## 将 Proof 降级为测试通过

丢失的是测试与语义承诺之间可能发生漂移的关系。

## 将 Freshness 降级为文档卫生

丢失的是信息可靠性对 Agent 自主权限的直接影响。

## 将 AGE 降级为 Skill

丢失的是项目语义结构与可调用过程能力之间的层级差异。

## 将 Mission Driver 升格为 AGE 本身

丢失的是方向定义与控制编排之间的区别。

## 将 Mission Driver 降级为工作流引擎

丢失的是它对仓库化项目连续性的持续执行和压力测试作用。

---

# 结语：AGE 工程化的是项目自身的连续性

AGE 不是为了让 AI 更严格地服从流程，也不是为了给 Agent 增加更多文档、Skill 和检查项。

它要处理的是一个更基础的问题：

> 当开发主体不再连续时，如何让项目仍然保持连续？

这个连续性不能只依赖源码，因为源码只能说明当前实现；不能只依赖测试，因为测试可能发生 Proof Drift；不能只依赖文档，因为文档可能过期；不能只依赖 Git，因为历史事件不等于轨迹语义；也不能只依赖 Mission Driver，因为持续执行本身不会产生正确方向。

项目连续性必须被拆解并外化为：

- 期望吸引子；
- Owner 与 Precedence；
- Proof Relation；
- Freshness；
- Closure；
- Trajectory Memory；
- Negative Knowledge；
- 多时间尺度 Audit；
- 方向修改的治理权限。

在此基础上，Harness 才能把期望结构转化为局部控制，Mission Driver 才能让这些控制跨会话持续运行。

最关键的关系可以压缩为：

> **期望吸引子定义项目希望长期保持什么；实际吸引子揭示项目事实上反复走向什么；AGE 通过仓库语义结构、Harness 和多时间尺度闭环，使二者持续对齐；Mission Driver 则让这一对齐过程能够脱离人的同步参与而长期运行。**

因此，Mission Driver 不是 AGE 的起点。

它是一个执行器，也是一个检验器：当当前 Session 结束、当前执行者离开之后，项目是否已经拥有足够完整的方向、证明、记忆和裁决结构，能够继续作为同一个项目演化下去。

而 AGE 最终要建立的，正是这种能力：

> **不是让某个 Agent 记住项目，而是让项目本身不再遗忘自己。**
