## Current Baseline

- plan 2026-07-25-1057-2 已为 manufacturing 域创建 10 个 per-mutation Processor 文件（2 实体 × 5 S-mutation），当前全部为**空心委托**：`@Inject ErpMfg{WorkOrder,SubcontractOrder}Processor processor`，public S-mutation 方法 `return processor.method(id, context)` 一行回委托；抽象基类 step override 为 `null`/空体（`// not reached: main method delegates to monolithic Processor`）。空心形状是蓄意脚手架。
- 2 个 facade Processor 持有全部真实编排逻辑，位于同包 `app.erp.mfg.service.processor`：
  - `ErpMfgWorkOrderProcessor`（5 S-mutation + protected step：`doSubmit`/`doApprove`/`doReject`/`doReverseApprove`/`doWithdrawSubmit`/`validate*`）
  - `ErpMfgSubcontractOrderProcessor`（5 S-mutation + protected step）
- **错误纪律：facade 100% NopException + ErpMfgErrors ErrorCode**（`ERR_INVALID_STATUS_TRANSITION`、`ERR_WORK_ORDER_NOT_FOUND`、`ERR_SUBCONTRACT_ILLEGAL_STATUS_TRANSITION` 等），facade 内零 NopScriptError。
- **xbiz `<source>` 分类（实测，非均匀）**：
  - **8 个 delegation 可达**（每实体 4：submitForApproval/approve/reject/reverseApprove）——xbiz `<source>` = `inject('...Processor').method(...)` 委托 per-mutation（空心）→ facade。
  - **2 个 inline-script 休眠**——`ErpMfgWorkOrder.xbiz` 与 `ErpMfgSubcontractOrder.xbiz` 的 `withdrawApproval` 是 **inline `<c:script>`**（不经 per-mutation `*WithdrawApprovalProcessor`）：内联脚本 `requireEntity` + 状态守卫 `throw new NopScriptError("nop.err.wf.approve.invalid-status")` + 设 `approveStatus='UNSUBMITTED'`。2 个 `*WithdrawApprovalProcessor` 文件注册为 bean 但**无任何 xbiz/Java 调用方**——运行时死代码。**这是范围内首个有真实 inline-script 提取需求的域**（R5.1 purchase 实测 inline 为空操作 N/A）。
- **BizModel**：`ErpMfgWorkOrderBizModel` / `ErpMfgSubcontractOrderBizModel` 各 `@Inject` 单 facade，但**只声明 D-mutation**（start/stop/close/cancel/issueMaterials 等），无 S-mutation `@BizMutation`——S-mutation 全经 xbiz `<source>` → per-mutation → facade。BizModel 类 Javadoc 声称 S-mutation 来自平台 `approval-support.xbiz`——**此声明陈旧**（实体自身 `ErpMfg*.xbiz` 已 override 全部 5 个 S-mutation source）。
- **doReject/doReverseApprove 抽象骨架偏离风险（CRITICAL）**：
  - 抽象基类 `doReverseApprove` 设 **SUBMITTED**（Javadoc 明示「回到 SUBMITTED」）；两个 facade 的 `doReverseApprove` 设 **REJECTED**。若迁移改走基类模板将导致状态机回退（REJECTED→SUBMITTED 回归）。
  - 抽象基类 `doReject` 设 approvedBy/approvedAt；两个 facade 的 `doReject` **不设**。Subcontract `doReject` 额外写 `docStatus=REJECTED`（WorkOrder 不写）。
  - Pattern B custom public override 绕过基类模板，custom override 精确保留 facade 语义。
- **withdrawApproval 测试覆盖缺口（实测）**：mfg 域测试目录 grep `withdrawApproval` = 0 命中。该 mutation 的负向状态守卫（`非 SUBMITTED → 报错`）**无任何既有测试覆盖**——它是本 plan 唯一的真实 inline-script 提取路径，且错误码字符串/参数名将发生变化（`NopScriptError("nop.err.wf.approve.invalid-status")` + `.param(bizObjName/bizObjId/action/currentStatus/expectedStatus)` → `NopException` + domain ErrorCode 经 facade `illegalTransition` helper，参数名变为 `*_CODE/CURRENT_STATUS/EXPECTED_STATUS`）。这是**已知的可观察行为 delta**（roadmap 测试策略允许 NopScriptError→NopException 转换，但要求显式等价验证，非静默等价声明）——错误码等价须由**新增**断言建立，而非既有断言。
- **wf:wfName**：WorkOrder / SubcontractOrder xmeta 均为空壳，repo-wide grep `wf:wfName` 在 module-manufacturing 零命中——无工作流配置，`AbstractSubmitForApprovalProcessor.maybeStartWorkflow` 为空操作。
- 同包，无跨包问题；facade helper 全 `protected`（step）+ `public`（S-mutation 入口）。
- mfg 域既有测试全绿（31 测试文件），作为行为等价基线。无测试文件引用任何 per-mutation processor。

## Goals

- mfg 域全部 10 个 per-mutation Processor 各自自包含：8 个 delegation 类走 Pattern B custom public override（1:1 复刻 facade 编排流，经 facade protected helper 单一真相源）；2 个 withdrawApproval 经 inline-script 提取为 Java hook + xbiz `<source>` 改委托，`NopScriptError` → `NopException` 错误码语义等价。
- 8 个 delegation 类 per-mutation 经 mfg 域既有测试验证行为等价。
- 2 个 withdrawApproval per-mutation 提取后 xbiz 改委托激活运行时路径，错误码语义等价（`nop.err.wf.approve.invalid-status` → `NopException`+domain ErrorCode）经测试断言验证。
- 域特有约束保真：WorkOrder submit 需 `docStatus=DRAFT`、approve 需 `docStatus=SUBMITTED` 跨字段校验；Subcontract reject 写 `docStatus=REJECTED`；reverseApprove 目标态=REJECTED。

## Non- Goals

- D-mutation（start/stop/close/cancel/issueMaterials/receiveFinished 等）保留在 facade——MR5 范围外（roadmap 明示）。
- BizModel 配线 + beans.xml + xbiz 清理（除 withdrawApproval xbiz 改委托，属本 plan inline 提取的必要部分）——其余 BizModel→facade 重配线属 R5.8。
- `ErpMfgJobCard`、`ErpMfgScheduleToJobCard`（纯 D-mutation，无 S-mutation per-mutation 文件）——不在 R5.5 范围。
- 抽象骨架 doReject/doReverseApprove 默认行为修正——Pattern B 绕过基类模板（与 R5.1 一致）。
