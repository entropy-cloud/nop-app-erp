### A4.2.101（A1.31 SP-1）UC-QA-06 关键项否决缺失运行时触发面确认 — **维持 P1-RC-040**

- **L1 锚点**：`use-cases.md:107-109`「质检模板行.是否关键项==true 且该行不合格 → 整体质检单=REJECTED（关键项否决，无论其他项）；关键项不合格→不可让步（直接 REJECTED）」。
- **L3 live code 实测**：
  - **数据模型缺失确认**：`module-quality/model/app-erp-quality.orm.xml:326` `ErpQaInspectionTemplateLine` 仅有 `isRequired`（propId 8，displayName="是否必检"，stdSqlType=INTEGER），**无 `isCritical`/`criticalItem`/`关键项` 列**。grep `isCritical|criticalItem|关键项` 跨 `module-quality/`（含 dao/service/orm.xml，排除 target）= **ZERO HITS**（仅 SPC `SEVERITY_CRITICAL` 常量无关语义）。`isRequired`（是否必检）≠ `isCritical`（是否关键项）——必检是"是否对该项执行检验"，关键项是"该项不合格即整体否决"。
  - **评估器逻辑缺失确认**：`InspectionResultEvaluator.java:73-92` `aggregate` 方法——循环 `:79-85` 仅检测 `anyRejected`（任意行 REJECTED），无任何关键项加权分支；`:87-88` `!anyRejected → ACCEPTED`；`:90-92` `anyRejected && allowConcession → CONDITIONAL`（含 `allowConcession=true` 路径）。**关键项不合格 + allowConcession=true 运行时错误产出 CONDITIONAL**，直接违反 L1「关键项不合格→不可让步→直接 REJECTED」。`evaluateLine:28-52` 是通用 out-of-spec（specMin/specMax vs measuredValue 数值比较）REJECTED 探测，无关键项逻辑。
  - **业务域 allowConcession 触发面**：`recordResult` 方法（`IErpQaInspectionBiz.java:36-39`）经 `allowConcession` 入参驱动——业务域（检验员）可在 `recordResult` 调用时传 `allowConcession=true` 发起让步审批，运行时该参数是 CONDITIONAL 唯一入口，故关键项不合格场景若传 `allowConcession=true` 即错误放行。关键项数据无录入机制（模板行/质检单行均无 isCritical 列，无法标记某行为关键项），无法经 parameterId 或外部约定隐式标记（grep `parameterId` 在 evaluator/matcher 无关键项语义消费）。
- **裁决**：**维持 P1-RC-040 P1**（§2 P1①「功能完全缺失」——数据模型[isCritical 列] + 评估器逻辑[关键项否决分支] 双缺；§2 P1⑤「验收标准零断言」——testRejectedCriticalGoesRejected 命名误导实为 allowConcession=false 通用拒绝）。Q4=(a) 强制实现无例外（L1 + `inspection-integration.md §十:333` + §5.3:219-222 均显式声明关键项否决）。**非 P0**：CONDITIONAL 仍允许业务流转但不破坏 GL/库存（非会计过账破坏）+ 主路径[非关键项让步]正确 + 非核心循环断裂。
- **修复义务归 MR1**：触及 ORM 结构变更[`ErpQaInspectionTemplateLine` + `ErpQaInspectionLine` 加 `isCritical` 列] + `aggregate:73-92` 增关键项否决分支[关键项 REJECTED 行 → 强制整体 REJECTED，跳过 allowConcession] → **须 ask-first + 独立 plan-audit §5 ORM 结构变更类**。本审计 READ-ONLY 不改 InspectionResultEvaluator/ORM。
